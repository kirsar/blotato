# 1. Overall Architecture — implementation plan

**This file is the scope of record for what gets built.** It is deliberately **not a 1:1
mapping of [0.general-plan.md](./0.general-plan.md)** — that document is foundational
research, written to explore the problem at production scale and settle the reasoning
before anything was cut. This one reduces that to what fits a take-home time budget. Where
the two disagree, this file wins; where it is silent, the general plan holds.

Reducing scope is the point rather than a concession, so every omission below is a
decision with a reason, and none of them is discovered at build time.

**This file owns buildable wiring only** — Nest modules, DI tokens, entry points,
Procfile, domain-model field tables. It does not describe what each service *does* or
how it is sized: **per-service Logic, Load, Capacity, Host and Scale live in
[0.services.md](./0.services.md)**, and every number comes from
[0.capacity-planning.md](./0.capacity-planning.md). Nothing here re-derives or restates
either.

## What is deliberately not built

Ordered by how visible the absence is to someone reading the code.

| Omitted | Why | Designed in |
|---|---|---|
| **Webhook delivery to customers** (`/v1/subscriptions` answers `501`) | A delivery worker pointed at a customer-supplied URL is an SSRF path — address filtering, redirect re-checks and per-delivery timeouts are not deferrable, so half-building it is worse than not starting | [2.api-surface.md](./2.api-surface.md), current-api-overview.md #5 |
| **Platform-side ingestion webhooks** | Signature verification plus platform app review is disproportionate here; the schema is shaped so they can land later, since they are the single biggest quota lever | 0.capacity-planning.md §5 |
| **The `draft` automation level**, its promotion step, and the `GuardrailCheck` model | Promotion needs a human review surface. With nothing able to promote a `draft` row, the pipeline should not produce one | [4.agentic-integration.md](./4.agentic-integration.md), §1.2 |
| **Three worker processes** | One pipeline loop demonstrates the same flow end to end; the split is a `Procfile` and entry-point change, not a redesign | *The job*, below |
| **A delivery schedule table for outbound replies**, and with it any attempt counter or give-up threshold | **A consequence of the row above, not a separate decision.** `CommentSchedule` existed because a separate publisher claimed replies by due time, and putting that claim key on `Comment` would have indexed a churning column on the largest table in the schema. With one loop there is no second claim: a reply awaiting delivery is a `queued` `Comment` reached by walking down from the post the pass already holds, so `status` is the pending predicate and still needs no index, and retry cadence is inherited from `PostSchedule.nextPollAfter`. What that gives up is a give-up rule and a retry rhythm independent of the poll interval — neither of which a terminal failure needs | *Scheduling model*, below; [5.storage.md](./5.storage.md) |
| **Nest on the Fastify adapter** | §1.5's production argument stands, but the adapter swap is one line in the bootstrap and there is no throughput to exhibit against in-memory storage. Skipping it removes Fastify-specific typing, plugin registration and Swagger wiring from the build | §1.5 |
| **A separate Platform Emulator provider** | Both real providers are already mocked, so a third would emulate the emulation. Injected failure modes live on the two real entries instead | [3.social-media-integration.md](./3.social-media-integration.md) |
| **A live Postgres, and therefore Prisma's runtime client** | Every option costs the reviewer setup. A real server needs Docker or a hosted instance and credentials; PGlite avoids Docker but puts a WASM Postgres build and a Node-version dependency between `git clone` and a running demo. In-memory repositories behind DI tokens are the only version where `npm start` cannot fail on someone else's machine, which matters more here than exercising the ORM. **The schema is still checked, not just asserted:** `prisma validate` runs offline and `prisma migrate diff` generates the real Postgres DDL into a committed `init.sql` — enums, composite uniques and the raw partial index included — so a reviewer reads generated SQL rather than trusting the models. Making it live is a token rebinding | [5.storage.md](./5.storage.md) |
| **Real OAuth and a real secrets store** | `ICredentialStore.resolve(accountId, purpose)` is implemented by a fake, so the boundary is structurally real even though the secret behind it is not — no credential value ever appears in a signature or a log | [3.social-media-integration.md](./3.social-media-integration.md) |
| **Seven of the nine platforms** | Each is a registry entry plus a provider class, which is exactly the cost the design claims. Instagram and YouTube were chosen to disagree on sync mode, budget unit, budget scope, write cost, depth and length | [3.social-media-integration.md](./3.social-media-integration.md) |
| **`Platform` as a configurable database table** | Capability, scheduling constants and the quota model are a compile-time registry keyed by a native enum. The usual argument for a table — enabling a platform becomes a data toggle rather than a deploy — does not hold: a row cannot call an API, so a new platform needs a provider class either way, and the only thing data could do unaided is *disable* one, which is a config flag. A table becomes warranted when a platform needs persisted config that differs **per tenant**, which nothing here does. In exchange the constants are type-checked, diff in a pull request next to the provider they describe, and change by deploy rather than by migration plus a production `UPDATE` | [5.storage.md](./5.storage.md) |
| **Platform- and account-level quota rows** | A per-post signal cannot express platform-wide exhaustion, so an exhausted YouTube project still costs one local rejection per row. Named as a known gap rather than solved | *Quota handling*, below |
| **Reconciliation for non-idempotent platform writes** | No platform offers an idempotency key on comment creation, so a write that times out after acceptance can double-post. Closing it needs a read per retry against a budget where a YouTube write already costs 50 | [3.social-media-integration.md](./3.social-media-integration.md) |
| **A dedicated `ApiKey` model with rotation** | One hashed key on `User` is the simplest shape that works. Rotation and per-key revocation need one row per issued key, which matters the moment a key is compromised | *User*, below |
| **Multi-seat organizations** | `userId` is the tenant boundary. Several people at one company sharing accounts is a real production gap, deliberately not stretched to here | *User*, below |
| **Deletion detection** (`status: deleted`) | Forward-only cursor sync structurally cannot see a comment disappear. This is the one place the design is *behind* the live product, and §6.1's compliance requirement depends on it | current-api-overview.md #11 |
| **Author display names and avatars** | One `platformAccountId` and nothing else. Adding names back is a product decision with a privacy cost, not an improvement | [5.storage.md](./5.storage.md), §6.3 |

## One DI pattern, two kinds of Nest app

0.general-plan.md §1.4 defines six logical roles across five physical services. **This
take-home deploys two processes: `web` and one `worker`.** Both share one
dependency-injection pattern for consistency — but not one *kind* of Nest app. The
`web` process is a full Nest HTTP application (`NestFactory.create`): it needs
Nest's guards/interceptors/Swagger, which only exist for HTTP (§1.5's whole argument).
The worker is a Nest **application context**
(`NestFactory.createApplicationContext`) — Nest's DI container without an HTTP server,
guards, or controllers, used purely to construct and resolve a small, static dependency
graph (one repository set, one provider registry, one pipeline service) the same way the
web process does, instead of wiring it by hand. This costs one thin `@Module()`;
it buys one consistent construction pattern everywhere in the codebase, at the expense
of a small amount of ceremony the graph itself doesn't strictly need.

## Vertical slicing per platform, and where extensions attach

**Why:** each platform evolves on its own clock — Meta changes quota rules, YouTube
changes unit costs, X changes pricing — and none of those should touch another
platform's code. Slicing by platform rather than by layer is what makes "one dev/team owns
one platform" real instead of aspirational.

- **A platform module owns** its provider, its registry entry, and its extension
  repository *if it has one*. `InstagramModule`, `YouTubeModule`.
- **It does not own the scheduling *algorithm*.** Same algorithm everywhere; only the
  constants differ, and those live in the platform registry. A per-platform scheduler
  would duplicate one algorithm nine times to vary four numbers.
- **It does own *parsing* its platform's throttle response** into a normalized
  `ThrottledError` (Quota handling, below) — response formats differ, so only the
  provider can read them. It does **not** decide the next poll time; the scheduler
  applies one rule to the normalized facts. This is the seam where a per-platform
  `QuotaPolicy` would be extracted if that parsing ever grows past a few lines.
- **Iteration without naming**: a `@PlatformProvider()` decorator plus `DiscoveryService`
  (`@nestjs/core`) lets the registry populate itself from metadata. Nothing anywhere
  enumerates platforms by name or branches on `platform === …`.
- **Registration stays static imports.** Discovery finds what's *in the container*, not
  what's on disk. A glob-based `PlatformsModule.forRoot()` would remove the import list
  too, but adding a platform already means a provider, a registry entry, and possibly a
  migration — one *appended* line is noise, and appends don't conflict between devs.

**Which entities get per-platform extensions, and which stay single:**

| Entity | Extension? | Why |
|---|---|---|
| Platform itself | **No — it has no table** | Capability and constants are a code registry; the rest of the per-platform variation is *behaviour*, which lives in the provider class. A table becomes warranted only if a platform needs persisted **config** that differs per tenant. Not yet. |
| `Composition` | **No — impossible** | Platform-agnostic by definition (§1.2.a). It isn't on a platform, so it has nothing platform-specific to hold. Extensions attach at `Post`, which is the first entity that knows what platform it's on. |
| `Post` | **Yes — the extension point** | The first per-platform row. Sparse: a table exists only where a platform genuinely needs extra fields. Both built platforms qualify — `InstagramPost.mediaProductType` and `YouTubePost.privacyStatus`, each gating whether the post is pollable (see `Post` below). |
| `Comment` | **No — single entity for now** | Platform variance in comments is pass-through metadata this system never reads. Revisit only if a provider needs a stored field to fetch or post. |

**Extension mechanics** (see [5.storage.md](./5.storage.md) for the schema):

- **Shared primary key** — the extension's PK *is* its FK to `Post`
  (`postId`, `onDelete: Cascade`). No second surrogate id, so no `xPostId`/`postId`
  confusion; PK-to-PK join; one-to-one enforced by the key rather than by convention.
- **Sparse and optional.** Absence is the default. Enforced as *at most one* by the PK —
  "exactly one for this platform" would need a trigger, and isn't wanted.
- **`Post` does not declare the relations.** The provider's own repository fetches its
  extension by `postId`. Declaring them on the base would mean adding a platform edits
  the base model, which is precisely what vertical slicing is meant to avoid.
- **Existence is answered by the registry**, not by data and never by
  `information_schema` introspection.

## Shared providers (used by all four processes)

- **Repositories** — in-memory implementations (`InMemoryCommentRepository`,
  `InMemoryCompositionRepository`, `InMemoryPostRepository`,
  `InMemoryPostScheduleRepository`, `InMemoryAccountRepository`), `@Injectable()` and
  bound to DI tokens (`COMMENT_REPOSITORY`, `COMPOSITION_REPOSITORY`, `POST_REPOSITORY`,
  `POST_SCHEDULE_REPOSITORY`, `ACCOUNT_REPOSITORY`) — idempotency needs no repository of
  its own, since its two columns live on `Comment`, and outbound replies need none since
  they are `Comment` rows reached by post. This *is* the persistence for this
  take-home (Open decision points #2) — the Prisma schema in
  [5.storage.md](./5.storage.md) is a design artifact, not wired to a live DB. Binding
  by token, not concrete class, is what makes a later Prisma-backed swap a one-line
  provider change in each module, not a call-site change.
- **Platforms** — `ProviderRegistry` (code) + `ICommentProvider` implementations, also
  `@Injectable()`. The registry maps a `PlatformId` enum value to a provider class where
  one exists, and checks that platform's capability flags (Domain models below) before
  dispatching. Both halves are code, which is the point: the flags are type-checked
  against the class that has to honour them.
  **Two providers: Instagram and YouTube.** The pair is chosen to stress the interface
  rather than to look plausible — they diverge on budget unit (calls vs weighted units,
  where a YouTube insert costs 50x a list), budget scope (pooled-per-user vs
  fixed-per-project), read vs write limits, thread depth, length, sync mode, and auth
  artifact. The consequence *here* is that
  `IRateLimiter` cannot be `consume(1)` — the provider declares a per-operation cost and
  its budget scope.
  **There is no separate Platform Emulator.** Neither provider calls a real API — both
  generate comments and accept writes locally — so a third emulating provider would
  emulate the emulation. Hostile capability values and injected failures belong on the two
  real entries instead, where they also exercise the registry constants a reviewer can
  see. The other seven platforms Blotato publishes to (Facebook,
  Twitter, TikTok, Pinterest, Threads, Bluesky, LinkedIn) have no registry entry and no
  provider class — adding one is a code change, which is exactly the point
  (current-api-overview.md #1).

**What "shared" now means, given vertical slicing above** — the two entries differ and
the distinction matters:

- **Repositories are shared code.** One implementation, bound to one token, used
  identically by every process.
- **Platforms are a shared *registry over independently-owned modules*.** The registry
  is shared; the providers inside it are not. Each process imports the platform modules
  it needs and gets a registry assembled by discovery — the web process for capability
  validation, the workers for actual calls.
- **A platform module's extension repository is not shared at all.** Only its own
  provider touches it, which is what keeps `Post` ignorant of extensions.
- **Jobs are shared neither way** — each worker's module provides and resolves exactly
  one job service, never the others.

## OpenAPI

- **Code-first.** DTOs are the source; the `@nestjs/swagger` CLI plugin infers schemas
  from TypeScript types and `class-validator` decorators, so very few `@ApiProperty`
  annotations are needed. `DocumentBuilder` plus `SwaggerModule.setup` in the web entry
  point — roughly half an hour for something real.
- **Never spec-first for the server.** Generators produce awkward Nest controllers, drop
  validation decorators, and make round-tripping painful once hand-edited.
- **Generate the client, not the server.** `openapi-typescript` against the produced
  spec gives typed client types free.
- **Do not generate the Prisma schema from it.** API shape and storage shape genuinely
  differ — a create request is nested, storage is normalized. Three layers:
  Prisma-generated storage types, hand-written DTOs, hand-written mapper between. The
  mapper is where nesting becomes rows, and it's real logic.
- **Unbuilt-but-ours endpoints return `501`** with the standard error envelope, tagged
  `Designed — not implemented`. A 404 would be indistinguishable from a typo; a
  well-formed 501 proves routing and the error envelope work.
- **Another system's endpoints stay out.** Post authoring isn't this service's surface
  ([2.api-surface.md](./2.api-surface.md)), and publishing it here would assert
  ownership we don't have.
- **Why it earns its half hour:** persistence is in-memory and providers are mocked, so
  a reviewer can open Swagger UI and actually exercise the API with no database, no
  credentials, no setup. That turns the mock stack from a limitation into the demo.

## The job: one pipeline service, not three pollers

**The demo builds a single `CommentPipelineService`** (Open decision points #1). One
`@Injectable()`, one `run()` — a single pass that walks the whole flow end to end instead
of three services each claiming from the database and handing off through it.

```
run():
  1. claim    — due PostSchedule rows (FOR UPDATE SKIP LOCKED)
  2. read     — reader.listComments(post, schedule) → upsert Comments, advance the schedule
  3. generate — query the claimed posts for comments still owing a reply, oldest first
                (not step 2's output) → generator.generate(batch) → outbound rows at QUEUED
  4. write    — writer.createReply(...) for every QUEUED reply on the claimed posts →
                record the outcome
```

Steps 2 and 4 are the same platform port called in both directions
([3.social-media-integration.md](./3.social-media-integration.md)); step 3 is the stub
generator ([4.agentic-integration.md](./4.agentic-integration.md)). **What each step does
is specified in [0.services.md](./0.services.md)** under Scheduler-Retriever, Content
Generator and Reply Publisher, and is not repeated here — those remain the logical
services; this is one process running them in sequence.

**The claim is the only entry point, and steps 3 and 4 both scope themselves to it.**
Having claimed a post, the pass generates for *every* comment on it still owing a reply and
publishes *every* reply owed on it — whether that work arrived in this pass, through
`POST /v1/comments` since the last one, or from an attempt that failed earlier. Both are
found by walking down from the claimed post rather than by a second claim over a work
queue, which is what lets one loop cover every case from a single entry point.

**Step 3 therefore queries rather than consuming step 2's output**, and that distinction
carries the design's fault tolerance. "Owes a reply" is a stored predicate — a successful
generation writes a reply row, a deterministic failure writes one at `failed`, and both
exclude the comment permanently, while a provider-wide failure writes nothing and leaves it
eligible for the next pass. Reading step 2's return value instead would drop such a comment
the moment that post's polls come back empty, which is every post's normal end state. The
set drains rather than growing, so the query stays cheap: `(postId, platformCreatedAt)`
finds the post's comments and `(parentCommentId, isAuthor)` answers the anti-join.

- The loop lives in the entry script, not the service — `run()` is one pass, so it is
  callable from a test without a timer.
- Repositories, the provider registry and the generator arrive through constructor-
  injected DI tokens, same as everywhere else.
- The DB-as-queue pattern (§1.7) holds at the claim: `FOR UPDATE SKIP LOCKED` over
  `PostSchedule.nextPollAfter`, so two instances of this worker never take the same post.
  Within a pass, steps 2→3→4 hand rows along in memory.

Since `DRAFT` is out of scope, step 3 writes straight to `QUEUED` — no promotion step to
wire, in either worker or controller.

Splitting back into §1.4's three workers is a matter of moving each step into its own
service and letting the tables carry the handoff between them.

## The `web` process — the only HTTP app

- `ApiRootModule` (root) — imports `CommentsApiModule`, `HealthModule`,
  and binds the shared repositories/provider registry to their DI tokens so
  controllers/services get them through Nest's ordinary constructor injection. Also
  wires the global `ApiKeyGuard` (derives `userId`, §7.1), the
  exception filter (maps `AppError` to HTTP responses), and `@nestjs/swagger`'s
  `DocumentBuilder` — all HTTP-only concerns, which is why only this process's module
  needs them.
- **CommentsApiModule** — `CommentsController` (REST: list/get/create/delete — see
  [2.api-surface.md](./2.api-surface.md)), `CommentsService` (validation against the
  capability registry, idempotency delegation — real code, Open decision points #4),
  `IdempotencyInterceptor` scoped to `POST /comments`.
- **HealthModule** — `/health` endpoint (0.general-plan.md §10.1).

**No webhook module.** Platform-side callbacks are an *ingestion* decision, not an API
surface — whether the scheduler learns of a comment by polling or by being notified is
internal, and §3.2 records why they aren't built now. There is nothing for a controller
to expose, so there is no module.

Cross-cutting: idiomatic Nest validation is `class-validator`/`class-transformer` DTOs
via a global `ValidationPipe`, not zod — package.json should drop `zod` in favor of
those (`@nestjs/common`, `class-validator`, `class-transformer`) once implementation
starts.

## The worker process — a Nest application context, no inbound HTTP

**"No HTTP" here means no HTTP *server* — no listener, no routes, no inbound requests.
It does not mean no HTTP at all.** The worker makes outbound HTTP calls constantly: the
platform providers (Instagram/YouTube) in both directions, and the
agent service in the middle — that outbound traffic is the entire job. What it doesn't
have is anything an inbound request could hit: no guards, no controllers, no route table,
because nothing is ever supposed to call *it*.

`WorkerModule` provides the shared repositories, the provider registry and the generator,
plus the one pipeline service. The entry script boots it with
`NestFactory.createApplicationContext(...)` instead of `.create(...)` — no HTTP
listener, no guards, no controllers, just the DI container — resolves
`CommentPipelineService`, and runs it on an interval: `setTimeout`-based rather than
`setInterval`, so the adaptive/jittered interval from the Scheduler-Retriever spec
([0.services.md](./0.services.md)) can vary each cycle.

**What ships:**

| Process (`Procfile` entry, entry point) | Root module | Runs | Instances |
|---|---|---|---|
| `web` (`main.web.ts`) | `ApiRootModule` (`.create`, default Express adapter) | HTTP server | 3+ |
| `worker` (`main.worker.ts`) | `WorkerModule` (`.createApplicationContext`) | `CommentPipelineService` loop | 1+ |

**What §1.4 targets**, and what the pipeline's four steps map onto one-for-one:
`worker-retriever`, `worker-generator` and `worker-publisher` as separate dyno types, each
billed and scaled independently, because their load, external dependency and rate-limit
profiles all differ. The demo runs the same work in one loop.

Two processes, same codebase, same shared repository/provider classes and DI tokens, two
bootstraps. Using Nest's DI container in both (just not its HTTP layer in the worker) is a
deliberate consistency choice over hand-wiring, even though the worker's dependency graph
is small enough not to strictly require it.

`web` stays its own process — **HTTP vs. background is the one split this design actually
needs to demonstrate**, and it is the split that is load-bearing for the demo rather than
merely for production: the 30-second request timeout is why `POST /comments` returns
`201 queued` instead of calling a platform inline.

**Per the Scope guardrail in 0.general-plan.md: this is the ceiling, not a commitment to
build every piece with full polish.** What's explicitly real, per the Open decision
points: the three providers, the pipeline service, idempotency, and
`DELETE /v1/comments/:id`.

## Comment pipeline: two lifecycles, and callbacks

**Post lifecycle** — mostly outside this take-home's scope. A `Composition`/`Post` is
created by Blotato's existing post-scheduling/publishing feature — pre-existing, out
of scope here; this take-home starts from "a post already exists and was published."
From there: a human turns automation on for a `Composition` (§0 tier 2, which creates a
`PostSchedule` row, Domain models below) → the pipeline's step 1 claims a batch
of due posts → step 2 fetches their comments, and on the same pass recomputes
`PostSchedule.nextPollAfter` (the adaptive interval/backoff, §1.4). "Grab a batch" and
"update the schedule" are the same claim-and-process cycle, not two separate steps.

**Comment lifecycle** — two independent entry paths into the same `Comment` table,
both converging on the pipeline's step 4:

a. **Automated pipeline** (the automated path, §4): step 2
   fetches comments for an automated `Post` and saves them (inbound rows, `posted`) →
   step 3 takes the eligible inbound comments, calls the
   agent, and saves each reply — itself just another `Comment` row (outbound,
   `isAuthor: true`) — directly at `queued` → step 4 publishes them to the platform.
b. **Manual reply push** (the take-home's literal requirement): `POST /v1/comments`
   receives a request to reply to a comment and stores it directly at `queued` → the next
   pass that claims that post publishes it in step 4. Identical to (a) once the row
   exists — that convergence is the entire point of one shared table and one delivery
   path rather than two.

Step 4 does not distinguish the two, and does not distinguish either from a retry: all
three are simply a `queued` outbound row on a post this pass has claimed.

**Explicitly out of scope: the `draft` → approve → `queued` promotion step.** `draft`
stays a real value in `Comment.status`, since the schema models what the `draft`
automation level would need (§4.2/§5.2), but nothing in the built pipeline writes or
reads it: the pipeline's generation step writes straight to `queued`. The reason is simple —
if nothing can ever promote a `draft` row, the pipeline shouldn't produce one
([2.api-surface.md](./2.api-surface.md)'s "no promotion endpoint" note). `collect` and
`reply` are the two automation levels that ship.

## Domain models

Five core entities everything above operates on (`User`, `SocialAccount`,
`Composition`, `Post`, `Comment`), plus one supporting entity (`PostSchedule`) the
others attach to rather than duplicate. Not an
exhaustive list: the `Post` extensions (`InstagramPost`, `YouTubePost`) live in
[5.storage.md](./5.storage.md). Platform-specific shape (provider payloads) is
[3.social-media-integration.md](./3.social-media-integration.md)'s
territory; agent/autonomy behavior (guardrails, promotion logic) is
[4.agentic-integration.md](./4.agentic-integration.md)'s — this section only covers the
fields that exist regardless of platform or autonomy config. Full DDL belongs in
[5.storage.md](./5.storage.md), not here; this is the shape, not the schema.

### One canonical shape per entity; everything else is a projection of it

**These six types are the single source of truth, and no other shape in the codebase is
re-declared by hand.** Ports, responses and repository signatures are *derived* from them
with TypeScript's utility types — `Pick`, `Omit`, `Partial`, `Required` — which are
mapped types over `keyof`, so a projection is checked against its source at compile time
rather than kept in step by discipline.

The payoff is that drift becomes a build error. Rename `Comment.text` and every
projection of it fails to compile, which is precisely what a parallel hand-written
interface would not do.

Three places it does real work, each for a different reason:

- **Narrowing a port.** `FetchedComment` is `Pick<Comment, …>` intersected with the two
  fields that genuinely differ at the boundary, so the type states in one line which
  fields pass through untouched and which are the seam
  ([3.social-media-integration.md](./3.social-media-integration.md)).
- **Enforcing a security boundary in the type system.** `GET /v1/accounts` returns
  `Omit<SocialAccount, 'credentialRef' | 'userId'>`. The credential reference cannot reach
  a response because the type has no such field — not because a mapper remembered to drop
  it. The same shape keeps `idempotencyKey` and `requestHash` out of comment responses.
- **Passing entities whole where narrowing buys nothing.** The generator takes
  `[Post, Comment[]][]` and returns `Comment[]`
  ([4.agentic-integration.md](./4.agentic-integration.md)); the platform port takes `Post`,
  `PostSchedule` and `Comment` directly. A projection is worth writing when it removes
  something meaningful — a namespace mismatch, a credential, a field the callee cannot
  supply — and is ceremony otherwise.

**One deliberate exception: request DTOs are classes, not derived types.** `class-validator`
decorators need a class with real properties, and `@nestjs/swagger` infers the OpenAPI
schema from it, so a `Pick` cannot stand in. They stay honest by declaring
`implements Pick<Comment, 'text' | 'parentCommentId'>` — the decorators live on the class,
while the compiler still checks its field set and types against the domain.

### Platform is code, not a table

`SocialAccount`, `Post` and `Comment` carry a `platform` column typed as a
Postgres-native enum (`INSTAGRAM`, `YOUTUBE`), which stores as 4 bytes and indexes like
an integer while still reading as text in every query and log. Everything *about* a
platform — capability, scheduling constants, quota model — is a compile-time registry
keyed by that enum, spelled out in [5.storage.md](./5.storage.md).

A table was the earlier choice, on the reasoning that capability as data beats capability
scattered across `if (platform === …)` checks
([current-api-overview.md](./current-api-overview.md) #1). The first half of that still
holds and the registry delivers it. The second half — that a row makes enabling a
platform a data toggle rather than a deploy — did not survive contact with §8.1: a row
cannot call an API, so a new platform needs a provider class either way, and the only
thing data could ever do unaided was *disable* one. That is a config flag, not a table.

What the registry buys that rows did not: the constants are type-checked, they diff in a
pull request next to the provider code they describe, and changing one is a deploy rather
than a migration plus a production `UPDATE`. `ProviderRegistry` (above) maps the enum to
a provider class and consults the same registry entry before dispatching.

Two entries carry more weight than the rest. `maxCommentLength` is **enforced twice, not
once** — as validation before submitting, and as a prompt constraint fed into
the generation call itself. TikTok's 150-character cap sits under
a reply's typical token budget (0.capacity-planning.md §D), so catching an over-long
reply after the fact means discarding a paid LLM call that constraining generation up
front would have avoided. And `syncMode` decides which incremental-sync mechanism the
provider may rely on: `cursor` means forward-pagination chaining genuinely captures
what's new, so `PostSchedule.cursor` persists across polls; `since` means it does not, so
the provider filters by `PostSchedule.lastSyncedAt` and pages through that result set
without persisting a cursor. Guessing wrong silently drops or re-processes comments.

**Once there will be need to configure platforms withot code change, we will start moving it to DB table(s)**

### User

with `userId` as that id). A scope decision, not a claim that teams never matter: several

### Composition

**The authored piece only — not tied to a platform or account** (§1.2.a): `Composition`
1:N `Post`. One `Composition` fans out to several platforms; each platform-specific side
is a `Post`, below. `Post` names the per-platform row rather than the abstract
composition, matching the task brief's own language — "retrieve comments for a published
post."

**The alternative was `Post` / `PlatformPost`**, with `Post` as the authored piece.
Rejected on two grounds. Compatibility: Blotato's `postId` already means the
per-platform thing, so redefining it would make `?postId=` silently aggregate for every
existing integrator. And more importantly, **a customer's mental model of "post" is
already anchored to what they see on the platform** — changing what the word denotes is
a cost paid by everyone who reads the API, forever, to save one internal entity name.
`Composition` is mild jargon in one parameter; that's the cheaper side of the trade.

| `createdAt` | DateTime | |

### Post

One publication of a `Composition` to one `SocialAccount`. This is the entity
that actually gets tracked/polled for comments — tracking is inherently per-platform,
so this was always the right granularity, `Composition` never was.

| Field | Type | Notes |
|---|---|---|
| `id` | string | |
| `compositionId` | string (FK → Composition) | |
| `accountId` | string (FK → SocialAccount) | |
| `platform` | `PlatformId` | denormalized, matches the account's platform |
| `platformPostId` | string | platform-native id, set once actually published |
| `content` | string? | per-platform caption override (length/hashtag differences, §1.2.a) — null = use `Composition.content`; closes §1.1's flagged missing-caption gap |
| `publishedAt` | DateTime? | null = not live yet. **The only liveness signal needed** |
| `createdAt` | DateTime | |

**There is no `status` column.** A `draft | scheduled | published | failed` lifecycle
models authoring, and this system never authors — it consumes posts that already exist,
so every row would sit at `published` forever. `publishedAt` being non-null carries the
one bit actually read, and dropping the enum also removes a `draft` value that collided
confusingly with `Comment.status`'s unrelated one.

Automation level and all scheduling/backoff state (§0 tier 2, §1.4) live
on `PostSchedule`, described after `Comment`, below — not here. `Post` stays purely
identity and content.

**Why `Post` needs to be in the DB at all**, given this system never authors posts:

- **It's the FK target.** `Comment` and `PostSchedule` both reference it, and Postgres
  has no cross-table primary key — nine platform tables cannot be one referenceable
  target. This alone settles it.
- **It's what the scheduler claims.** `FOR UPDATE SKIP LOCKED` needs rows in one table;
  a union across platform tables can't do it.
- **It carries genuinely shared fields.** `platformPostId`, `accountId`, `platform`,
  `content`, `publishedAt` are identical in shape on all nine platforms and all five are
  read by this system. It isn't a shim invented to hold ids.

**Almost nothing platform-specific belongs here.** This system reads five things off a
`Post` — `platformPostId` to call the endpoint, `platform` to pick the provider,
`accountId` for credentials and budget, `content` for reply-generation context, and
`publishedAt` to know it's live. Almost all platform variance in a post is
*authoring* variance (media dimensions, targeting, thread construction) and authoring is
out of scope. Instagram's permalink and YouTube's `channelId` are never read, and
YouTube's video id *is* the `platformPostId`.

The rule for adding an extension field, therefore: **the comment fetch or write must
depend on it.** Receiving it from the platform is not enough. Exactly one field per
built platform meets that bar, and both are below.

### InstagramPost

Extension of `Post`, shared primary key. Instagram's `media_product_type` decides
whether the post can be polled at all: **Stories have no comments** — audience replies
arrive as DMs — while Feed posts and Reels do, under different behaviour. The provider
reads it before scheduling anything.

| Field | Type | Notes |
|---|---|---|
| `postId` | string (PK, FK → Post, cascade) | the extension's identity *is* its parent's — no separate surrogate id |
| `mediaProductType` | `FEED \| REELS \| STORY \| AD` | gates pollability. **Terminal** — a Story never becomes commentable, so such a post is retired permanently rather than re-checked |

### YouTubePost

Extension of `Post`, shared primary key. Same gating role, opposite temporal
character: a **private video's comments are inaccessible**, but privacy can be flipped
at any time, so the post must keep being checked rather than retired.

| Field | Type | Notes |
|---|---|---|
| `postId` | string (PK, FK → Post, cascade) | as above |
| `privacyStatus` | `public \| unlisted \| private` | gates pollability. **Transient** — unlike a Story, this can change, so `private` suspends polling without retiring the post |

**Why these two justify the mechanism rather than a base `commentsAvailable` boolean.**
The boolean is the obvious simplification and it loses the thing the scheduler acts on:
a Story is permanently uncommentable and should be retired, a private video is
temporarily inaccessible and should be re-checked. Collapsing both to "not available"
erases precisely the retire-versus-keep-polling distinction, and only the platform's own
vocabulary carries it.

**The stronger motivating case remains X**, which isn't among the built providers.
Replies there *are* posts, so fetching a thread needs a `conversationId` that no base
field carries — the fetch cannot be made at all without it. Instagram and YouTube
demonstrate the mechanism; X is where it becomes unavoidable.

### Comment

Covers both inbound (audience) and outbound (our replies) rows via `isAuthor`,
self-referencing through `parentCommentId`. Always targets a `Post`, never a bare
`Composition` — a reply is inherently platform-specific (§1.2.a).

**Scope decision: we never observe or reply to posts outside what we track.** Unlike
Blotato's real API (whose `postId` is nullable specifically for a comment/reply on a
platform post it doesn't track), this design has no ad hoc path in or out — inbound
comments only arrive via the pipeline polling a tracked `Post`, and a
reply can only target a comment that already exists on one. So `postId` is **never
null**, on either inbound or outbound rows.

| Field | Type | Notes |
|---|---|---|

| `platformAccountId` | string | the author's account id **on the platform**. `PostSchedule`; inbound comments still owing a reply and outbound replies awaiting
delivery are both reached by walking down from the claimed post within the same pass. That
is what lets `Comment` carry no due-time column and no index on `status`.

### Scheduling model

**`PostSchedule`** (supporting — 1:1 with `Post`, not one of the five core entities)

| Field | Type | Notes |
|---|---|---|
| `postId` | string (FK → Post, 1:1) | the row is **materialized when the post's effective level exceeds `OFF`** and retired when it falls back, so `OFF` has exactly one representation: no row (§0 tier 2) |
| `commentAutomationLevel` | `AutomationLevel?` | the *post's* level, stored here because this is the post's 1:1 automation-state table and `PUT /v1/posts/:id/automation` writes it. Null = don't lower. Rung 3 of the cap |
| `nextPollAfter` | DateTime | the scheduler's claim key (§1.4) |
| `pollIntervalSec` | number | current adaptive interval |
| `emptyPollCount` | number | drives geometric backoff on consecutive empty polls |
| `commentVelocity` | number? | decaying average, comments/hour — drives the target-yield interval calculation |
| `cursor` | string? | provider pagination cursor — used when the registry's `syncMode` is `cursor`; unused (stays null) when `since` |
| `lastSyncedAt` | DateTime? | used as the `since` filter when the registry's `syncMode` is `since`; also feeds the `commentVelocity` elapsed-time calc regardless of sync mode |
| `retiredAt` | DateTime? | polling stopped (~14-day mark, §1.4); `Post`'s data still retained to 45 days — a separate threshold from deletion |
| `createdAt` | DateTime | when the post was subscribed |

**One `PostSchedule` serves every platform**, and it survives because three things were
pushed elsewhere: platform-specific *fetch inputs* to `Post` extensions, *policy* to
registry constants, and *quota state* to account- or project-grain budget rows. What's
left is genuinely uniform — pagination is an opaque string everywhere, cursor-vs-`since`
is two nullable columns plus a flag, and the adaptive algorithm is identical with only
its constants varying.

Two things would break that and neither is present: a platform needing *persistent*
multi-cursor state (YouTube comes closest, since threads and their replies paginate
separately, but that's transient within one poll), or a platform whose poll unit isn't
the post.

**There is no second schedule table for outbound replies.** `PostSchedule` is the only
one. A reply awaiting delivery is an outbound `Comment` at `queued`, and the pipeline
reaches it by walking down from the post it has already claimed — so the pending predicate
is a column that already exists, and `status` never needs an index. `Comment` takes inserts
plus one heap-only status write per reply, which is what keeps the largest table in the
schema append-mostly.

Retry cadence comes from `PostSchedule` too: a transiently-failed reply is still `queued`
when its post next falls due, so the adaptive poll interval paces retries as a side effect.
That inherits backoff for free and gives up two things — a give-up threshold, and a retry
rhythm independent of the post's poll interval — neither of which a terminal failure needs,
since a rejected reply is written `failed` on the first attempt and never revisited.

### Quota handling — one uniform interface now, `QuotaPolicy` if it grows

**Throttle rules differ between platforms in kind, not degree** — this is the one place
scheduling behaviour is genuinely platform-specific rather than a constant:

- **Meta** returns `X-App-Usage` as a percentage of a rolling-hour pool → exponential
  backoff is the right response.
- **YouTube** returns `quotaExceeded` against a **daily** budget resetting at midnight
  Pacific → the right response is *sleep until reset*. Backing off exponentially against
  a daily quota either burns hours or hammers a wall.
- **X** returns rate-limit reset headers, and is metered in money as well as calls.

**Current answer: the provider reports a fact, the scheduler makes the decision.**

- **The provider normalizes, it does not schedule.** What it uniquely knows is the
  *response format* — YouTube signals exhaustion as `quotaExceeded`, Meta puts usage in
  `X-App-Usage`, X uses reset headers. Parsing that is its job; deciding when to poll
  next is not.
- `ICommentProvider` throws a normalized
  `ThrottledError { resetAt?, retryAfterSec?, usagePct? }` carrying whatever the
  platform actually said, and nothing it didn't.
- **The scheduler owns one uniform rule** over that: use `resetAt` if present, else
  `now + retryAfterSec` if present, else its own exponential backoff. Platform
  difference lives entirely in the parsing; the decision stays in one place.
- **Cost and scope stay declarative** rather than branching — `costPerRead` /
  `costPerWrite` (YouTube: list 1 unit, insert 50) and `budgetScope` (pooled-per-user vs
  fixed-per-project) are registry constants the rate limiter reads, not `if` statements.
- **Known gap, deliberately not solved yet:** a per-post signal can't express
  *platform-wide* exhaustion. If YouTube's project quota is gone until midnight PT, the
  next claim still grabs a batch of YouTube posts and burns a call per row discovering
  it. The fix is a platform-level budget row that the claim query checks, which also
  gives per-account budget state a home (§3.3) — deferred as disproportionate for now.

**When to extract a per-platform `QuotaPolicy` class:**

- **Trigger, not a schedule**: when `interpretThrottle` grows past a few lines per
  platform, or when a platform needs quota *state* the provider shouldn't own — a
  running daily-unit tally, a reserve held back for writes, a money budget.
- **The justification is change cadence**, not tidiness: the content API and the quota
  rules move independently. YouTube's comment payload has been stable for years while
  its unit costs have not.
- **Named `QuotaPolicy` or `RateLimitPolicy`, never `ScheduleUpdater`** — it doesn't
  update the schedule, the scheduler does. It answers what an operation costs, what
  scope the budget has, and when we may act again.
- **Not extracted now.** For two platforms it's a handful of lines, and a class per
  platform to hold them would be ceremony (0.session-handoff.md, open item 7).

## API service scaling (reverse proxy / DNS)

On Heroku: web dynos scale horizontally (`heroku ps:scale web=N`); Heroku's router *is*
the reverse proxy/load balancer, round-robining across dynos automatically, with TLS
termination and DNS handled for the app's Heroku or custom domain — nothing we build
ourselves. Run 3+ web dynos from the start for real redundancy (2 is only bare-minimum
failure survival with no spare capacity left), not because the load (low-hundreds
req/sec at peak, per §1.4) needs it — a single modern Node process comfortably
handles that for JSON CRUD backed by indexed Postgres queries, on either HTTP adapter. Scale further only on
observed CPU/response-time pressure. For global growth, a latency floor no amount of
single-region scaling fixes: a custom DNS resolver (GeoDNS/GSLB, or anycast) routing
each client to its nearest region, whose reverse proxy then load-balances locally as
above — not needed yet.

## Hosting: Heroku vs. EC2 vs. EKS, and concrete Heroku limits to design around

Recommendation: **Heroku**, for the take-home and near-term. Concrete limits worth
designing around, several of which are already load-bearing in this design:

- **30-second request timeout (H12)** per web-dyno HTTP request — this is a concrete
  reason `POST /comments` must return `201 queued` immediately (never `draft` — out of
  scope end to end, [2.api-surface.md](./2.api-surface.md)) rather than synchronously
  calling the platform: a slow or rate-limited platform call could easily
  exceed 30s.
- **Dynos cycle/restart** (at least every 24h — "dyno cycling" — and can restart
  anytime) — no durable in-process state survives. Reinforces why the retrieval,
  reply-generation, and posting queues all live in Postgres (`Post`/
  `Comment.status`, see [5.storage.md](./5.storage.md)) rather than an in-memory interval: a restart
  mid-poll loses nothing, since state lives in the DB, not the process.
- **Ephemeral filesystem** — nothing durable can live on local disk; anything that
  needs to persist goes to Postgres or S3.
- **Dyno tiers** — Standard dynos share CPU with fixed RAM (512MB-1GB); Performance
  dynos give dedicated CPU and 2.5-14GB RAM. At real (not take-home) scale, Performance
  tier or a move off Heroku would follow CPU/RAM pressure, not request-count alone.
- **Postgres connection limits** — Heroku Postgres plans cap concurrent connections
  (e.g. roughly 120 on Standard tiers); with multiple dynos each holding a connection
  pool, this needs PgBouncer or a tuned pool size, not one default-sized pool per dyno
  assumed free. Moot for this take-home's in-memory persistence (Open decision points
  #2), but real once Prisma is wired to a live DB.
- **Worker dynos** — the target design is three separate dyno types (Nest application
  contexts, no inbound HTTP listener — they still make plenty of *outbound* HTTP calls
  to platforms/the AI provider), one per job service, each billed and scaled
  independently of web dynos and of each other, since their load, external dependency,
  and rate-limit profile all differ (§1.4). **This take-home ships one `worker` dyno
  running the whole pipeline in one loop** (see *The job*, above) — one dyno type instead
  of three, at the cost of the independent-scaling and isolation properties the split
  design has.

**Do we pay for these instances 24/7, or can this flex for rush hours?** 24/7, by
default — Heroku dynos bill continuously while scaled up; they don't scale to zero, and
native autoscaling is a Performance-tier, web-dyno-only feature (response-time
triggered), not available for worker dynos at all. This is less wasteful than it sounds
here: the §1.4 figures are already worst-case peak assumptions ("every post
saturates"), so flat 24/7 provisioning at those counts already covers rush-hour peaks
without needing dynamic autoscaling. Flat provisioning for this take-home; scheduled
scaling (Heroku Scheduler, cutting worker dyno counts during known-low-traffic windows)
is the real lever if cost mattered later — named as the trigger, not built.

EC2 would trade this convenience for full infra control — worth it only once the limits
above are actually being hit, not preemptively. EKS is the infrastructure a genuine
microservices decomposition would want (independent scaling/deployment per service,
sophisticated rollout patterns); nothing about the four-deployables-one-repo shape
below or the capacity figures justifies that operational overhead now.

**`*.contract.ts` means the file declares interfaces and types only** — no classes, no
decorators, no framework imports. The suffix is applied consistently, so a glob over
`**/*.contract.ts` is the whole set of ports in the system.

**The in-memory store enforces constraints, not just storage.** `InMemoryRepository<T>` is
the one substantial class — a primary `Map` plus **declared unique keys** backed by
secondary maps, and clone-on-read/write so a caller mutating a returned object cannot
silently mutate the store. The five concrete repositories add only their own query methods.

Two uniques are load-bearing and a fake that skipped them would agree with the design
rather than test it: `(userId, idempotencyKey)` is the whole of the idempotency contract
([2.api-surface.md](./2.api-surface.md)), and `(userId, platform, platformCommentId)` is
what makes re-ingesting our own reply an upsert — the mitigation for the platform's
non-idempotent write ([3.social-media-integration.md](./3.social-media-integration.md)).

**Transactional writes hold without a transaction manager.**
`POST /v1/compositions` is all-or-nothing across a composition, its posts and their
extension rows; in memory that follows from the event loop, provided the commit block
validates everything first and then writes with no `await` in the middle.

**No barrel files.** A barrel makes import cycles easy to create, and in Nest a cycle
surfaces as an `undefined` provider at runtime rather than a compile error. The problem
barrels solve — long relative paths — is solved instead by `tsconfig` path aliases
(`@domain/*`, `@platforms/*`, `@storage/*`). Barrels earn their place at a published
package boundary; there is none here.

**`scheduling.ts` and `batching.ts` are separate files for the same reason:** both are pure
functions over plain data — the adaptive interval from 0.capacity-planning.md block 2, and
the batch partitioning from [4.agentic-integration.md](./4.agentic-integration.md) — so they
are the two places where the design's actual reasoning is directly testable without a
provider, a database, or a Nest context.

Trigger to reconsider: once a specific worker genuinely needs independent
scaling/deployment as a separate *build artifact* *and* multiple teams are shipping
into it on different cadences, two costs start to bite that a monorepo doesn't solve
for free —
PR/merge contention between unrelated teams' changes, and the need for dedicated
in-house tooling (a real build-graph tool like Nx/Turborepo/Bazel for incremental
builds/tests and remote caching, rather than rebuilding everything on every change).
Until either is actually happening, that tooling investment would be solving a problem
this project doesn't have yet.
