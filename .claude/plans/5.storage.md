# 5. Storage — implementation plan

Decisions and rationale: [0.foundational-research.md](./0.foundational-research.md) §5. Entity *shape*:
[1.overall-architecture.md](./1.overall-architecture.md), Domain models. **This file
owns the DDL only** — nothing here re-argues a decision.

**Scope guardrail:** this is the *designed* schema. The take-home builds the core
(`SocialAccount`, `Composition`, `Post`, `Comment`, `PostSchedule`) against in-memory
repositories; `User` is schema-only, not wired to real auth.

## Platform is code, not a table

Everything that used to be `Platform` rows — capability, scheduling policy, quota model —
is a compile-time registry keyed by a Postgres-native enum. The old argument for a table
was that enabling a platform becomes a data toggle rather than a deploy. That argument
never held: a row cannot call an API, so a new platform needs provider code regardless,
and the only thing data could ever do was *disable* one, which a config flag does.

```ts
export const PLATFORMS: Record<PlatformId, PlatformSpec> = {
  INSTAGRAM: {
    name: 'Instagram',
    enabled: true, supportsComments: true, supportsDelete: true,
    maxReplyDepth: 1, maxCommentLength: 2200,
    syncMode: 'cursor',
    poll:   { minIntervalSec: 60, maxIntervalSec: 21_600, backoffFactor: 2, targetYield: 10 },
    budget: { unit: 'calls', scope: 'app', costPerRead: 1, costPerWrite: 1 },
  },
  YOUTUBE: {
    name: 'YouTube',
    enabled: true, supportsComments: true, supportsDelete: true,
    maxReplyDepth: 5, maxCommentLength: 10_000,
    syncMode: 'since',
    poll:   { minIntervalSec: 300, maxIntervalSec: 43_200, backoffFactor: 2, targetYield: 20 },
    budget: { unit: 'units', scope: 'project', costPerRead: 1, costPerWrite: 50 },
  },
};
```

`syncMode`, `budget.unit` and `budget.scope` are TypeScript string unions here rather
than database enums. Nothing filters or joins on them — they are read once per poll to
configure a provider call — so a database enum bought type-safety we get for free in
code, at the cost of a migration to change a constant.

```prisma
// ── Enums that are genuinely per-row data ─────────────────────────────────────
// Postgres-native enum: stored as a 4-byte OID, so it indexes and sorts like an int,
// but reads and writes as text in every query and log. No join to know the platform.
enum PlatformId { INSTAGRAM YOUTUBE }

enum CommentStatus { DRAFT QUEUED PROCESSING POSTED FAILED DELETED }

// Ordered — each level switches on one more worker. The ordering is load-bearing:
// effective = min(max, composition, post), and min needs a ranked set.
// Prisma enums carry no order, so comparison uses a rank() helper in code.
enum AutomationLevel { OFF COLLECT DRAFT REPLY }

// ── Tenant ────────────────────────────────────────────────────────────────────
model User {
  id           String   @id @default(cuid())
  displayName  String
  hashedApiKey String   @unique   // SHA-256, not bcrypt (§1.8)
  createdAt    DateTime @default(now())

  // A cap, never the level anything runs at. Rung 1 of three
  maxCommentAutomationLevel AutomationLevel @default(COLLECT)

  accounts     SocialAccount[]
  compositions Composition[]
}

model SocialAccount {
  id                String     @id @default(cuid())
  userId            String
  user              User       @relation(fields: [userId], references: [id])
  platform          PlatformId
  platformAccountId String
  displayName       String
  credentialRef     String     // secrets-store id (§7.3) — never a token value
  createdAt         DateTime   @default(now())

  posts    Post[]
  comments Comment[]

  // Scoped to the tenant, not global — see notes
  @@unique([userId, platform, platformAccountId])
}

// ── Composition 1:N Post (§1.2.a) ─────────────────────────────────────────────
model Composition {
  id        String   @id @default(cuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id])
  content   String   // authored original; Post.content overrides per platform
  createdAt DateTime @default(now())

  // Can only lower what the user's max allows. Rung 2
  commentAutomationLevel AutomationLevel?

  posts Post[]
}

model Post {
  id             String        @id @default(cuid())
  compositionId  String
  composition    Composition   @relation(fields: [compositionId], references: [id])
  userId         String        // denormalized from Composition — RLS + the unique below
  accountId      String
  account        SocialAccount @relation(fields: [accountId], references: [id])
  platform       PlatformId
  platformPostId String
  content        String?       // null = use Composition.content
  publishedAt    DateTime?     // null = not live yet. The only liveness signal needed
  createdAt      DateTime      @default(now())

  schedule PostSchedule?
  comments Comment[]

  @@unique([userId, platform, platformPostId])  // two tenants may track one public post
}

// ── Post extensions: sparse, shared PK, only where a fetch depends on the field ─
model InstagramPost {
  postId           String @id                     // PK *is* the FK — no surrogate id
  post             Post   @relation(fields: [postId], references: [id], onDelete: Cascade)
  mediaProductType String // FEED | REELS | STORY | AD — Stories have no comments.
                          // Terminal: a Story never becomes commentable, so retire it
}

model YouTubePost {
  postId        String @id
  post          Post   @relation(fields: [postId], references: [id], onDelete: Cascade)
  privacyStatus String // public | unlisted | private — private hides comments.
                       // Transient: can flip back, so suspend rather than retire
}

// ── Automation + polling state. Row is materialized when effective level > OFF ─
model PostSchedule {
  postId          String           @id
  post            Post             @relation(fields: [postId], references: [id], onDelete: Cascade)

  // The POST's level, stored here because this is the post's 1:1 automation table. Rung 3
  commentAutomationLevel AutomationLevel?

  nextPollAfter   DateTime         // the scheduler's claim key; jittered
  pollIntervalSec Int
  emptyPollCount  Int              @default(0)
  commentVelocity Float?           // decaying avg, comments/hour → target-yield interval
  cursor          String?          // used when the platform's syncMode is 'cursor'
  lastSyncedAt    DateTime?        // the `since` filter otherwise; velocity elapsed-time either way
  retiredAt       DateTime?        // polling stopped (~14d); data retained to 45d
  createdAt       DateTime         @default(now())

  @@index([nextPollAfter])         // no partial predicate needed — see notes
}

// ── Comment: inbound audience rows and our outbound replies, one table ────────
model Comment {
  id                String        @id @default(cuid())
  userId            String        // denormalized so RLS needn't join through account
  accountId         String
  account           SocialAccount @relation(fields: [accountId], references: [id])
  platform          PlatformId
  postId            String        // never null — we only observe posts we track
  post              Post          @relation(fields: [postId], references: [id])
  compositionId     String        // denormalized — GET /comments?compositionId= is a core read
  parentCommentId   String?       // OUR cuid. Bare scalar, deliberately no FK — see notes

  platformPostId    String
  platformCommentId String?       // null until an outbound reply is confirmed
  platformParentCommentId String? // the PLATFORM's parent id — a different namespace from
                                  // parentCommentId above, so one column can't serve both
  platformAccountId String        // the author's account id ON THE PLATFORM. Always set:
                                  // isAuthor = (this == SocialAccount.platformAccountId).
                                  // With `text`, the only audience PII stored; erasure
                                  // nulls both (§6.3)
  isAuthor          Boolean       // true = our own reply
  text              String
  platformCreatedAt DateTime      // when it was written ON THE PLATFORM — not createdAt,
                                  // which is when we ingested it. See notes

  // Outcome AND the pending predicate: QUEUED on an outbound row = a reply is still owed.
  // Deliberately unindexed — the pipeline reaches these by post, so the one write per
  // reply stays HOT (see notes)
  status            CommentStatus
  errorCode         String?       // last failure, ours or the platform's — see notes
  errorMessage      String?

  // Idempotency — contract in 2.api-surface.md. Null on every inbound comment and
  // every generator-written reply, hence the partial index (raw SQL; Prisma can't):
  //   CREATE UNIQUE INDEX ON comment (user_id, idempotency_key)
  //     WHERE idempotency_key IS NOT NULL;
  idempotencyKey    String?
  requestHash       String?

  createdAt         DateTime      @default(now())
  updatedAt         DateTime      @updatedAt

  @@unique([userId, platform, platformCommentId])  // re-ingesting our own reply is an upsert
  @@index([compositionId, platformCreatedAt])  // ?compositionId= — across platforms
  @@index([postId, platformCreatedAt])         // ?postId= — one platform
  @@index([parentCommentId, isAuthor])         // "already replied?" — the generator's claim query
}
```

## Notes — the non-obvious parts only

**Naming rule: `user` is ours, `account` is the platform's.** `User`/`userId` never
refers to anything on a social platform; anything platform-side is an *account*. That's
why the author of a comment is `platformAccountId` rather than a "user" id.

**RLS is Postgres row-level security** — a policy attached to the table that filters
which rows a session may read, enforced by the database rather than re-stated in every
query. The policy is `user_id = current_setting('app.user_id')`, which is the whole
reason `userId` is denormalized onto `Post` and `Comment`: without it the policy joins
through `SocialAccount` on every row it checks, on the two largest tables in the schema.

**The relation arrays cost nothing.** `User.accounts`, `Post.comments` and the rest are
Prisma relation fields, not columns — no bytes on disk. The foreign key itself comes from
the owning side (the model holding the scalar and its `@relation`), but Prisma's schema
validator **refuses to compile a one-sided relation**, so the array is the mandatory
back-half of declaring the FK at all. Prisma also has **no lazy loading**: nothing is
fetched unless a query explicitly says `include`, so `user.accounts` can never quietly
pull every row. Their only real cost is a slightly longer model.

**`Comment.parentCommentId` is a bare scalar with no relation field, and that is the one
place the rule is broken on purpose.** A self-referential foreign key makes Postgres
verify the parent exists on *every* comment insert, and comment ingest is the hottest
write path in the system. The traversals we actually run are scalar queries
(`WHERE parentCommentId = ?`), never `include: { replies: true }`, so the constraint
would buy integrity we can assert at ingest for a per-row cost on the largest table.
`userId` and `compositionId` on `Comment` are bare scalars for the same reason.

**Two parent ids, because they are two namespaces.** `parentCommentId` is our cuid;
`platformParentCommentId` is what the platform returned. Ingest receives the second and
must translate to the first, so holding both lets that resolution be deferred or batched
instead of costing a lookup per comment, and it puts everything a reply needs on the
outbound row — which is what keeps the publisher from joining to the parent just to learn
where to post ([3.social-media-integration.md](./3.social-media-integration.md)).

**Two timestamps, for the same reason.** `createdAt` is when *we* ingested the row;
`platformCreatedAt` is when the comment was written on the platform. They agree to within a
poll interval in the normal case and diverge by hours after a slow poll or an outage, and a
caller filtering `GET /v1/comments?since=` means the platform's clock, not our
bookkeeping. Both listing indexes are therefore keyed on `platformCreatedAt`: it is what
the API filters and orders by, and it never changes once set, so it is as stable a keyset
cursor as ingest order would have been.

**`@@unique([userId, platform, platformAccountId])` is tenant-scoped, not global.** Two
different Blotato users may legitimately connect the same Instagram account — an agency
that manages a brand, and the brand itself. A global unique on
`(platform, platformAccountId)` would make whichever of them connects second fail with a
collision against a row they cannot see. The same reasoning gives `Post` its
`(userId, platform, platformPostId)` unique: both tenants then track the same public
post as two independent rows, each with its own schedule, automation level and comment
history, and neither can observe the other.

**`isAuthor` is derived, never trusted, and that column is never null.** At ingest:

```
comment.isAuthor = (comment.platformAccountId == socialAccount.platformAccountId)
```

Same field name on both sides, because it's the same kind of value. Deriving from the
platform's response rather than from our own records is what survives the case that
matters: if a reply posts but the status write fails, the next poll sees an unrecognised
comment, and anything keyed on our own bookkeeping would treat our reply as fresh
audience input — and reply to itself. `@@index([parentCommentId, isAuthor])` is the other
half of that guard, backing the generator's per-candidate question "have we already
replied to this one?" without reading the rows to find out.

**`errorCode`/`errorMessage` hold the last failure whatever its origin**, which is why
they are not named `platformError*`. Roughly half are ours — reply longer than the
platform's `maxCommentLength`, effective automation level too low to publish — and half
are the platform's, relayed from a 4xx. A caller debugging a stuck reply wants one field
to read, not two.

**`Comment` carries no delivery state, and needs none.** `status = QUEUED` on an outbound
row *is* the pending predicate, and the pipeline reaches those rows by walking down from
the post it already claimed ([1.overall-architecture.md](./1.overall-architecture.md)) —
never by scanning `Comment` for due work. So `status` stays out of every index, and the one
write per reply, from `QUEUED` to its terminal value, is a heap-only tuple update on a table
that otherwise only takes inserts. `Comment` holds `fillfactor` near 100 for the same
reason.

**Retry cadence comes from `PostSchedule`, so there is no second schedule table.** A reply
whose attempt failed transiently is simply still `QUEUED` when its post next comes due, and
the adaptive interval that paces polling paces retries with it. Backoff is therefore
inherited rather than implemented, at the cost of the two things a dedicated attempt
counter would buy: a give-up threshold, and a retry cadence independent of how often the
post is polled. Terminal failures do not depend on either — a rejected reply is written
`FAILED` on the first attempt and never reconsidered.

**Audience author identity is one column, not a table.** A comment stores the author's
`platformAccountId` and nothing else — no display name, no avatar. That matches what
Blotato stores today, and 0.current-api-overview.md #9 reads it as deliberate PII
minimization rather than an omission, which is the right call when the data is
third-party and pooled across tenants.

**There is no author lookup table**, and easing right-to-erasure — the usual argument for
one — does not survive contact with §6.3, which defines erasure as nulling
`platformAccountId` and `text` **on matching `Comment` rows**. A lookup keyed by account
would therefore be a *second* place to erase, not a replacement for the first. Keeping
author identity as one column makes erasure a single `UPDATE` against a single table, and
keeps an upsert off the hottest write path, since every ingested comment would otherwise
have to touch it.

The cost is that `GET /v1/comments` returns an opaque author id. Adding names back is a
product decision with a real privacy cost, not a straightforward improvement — which is
exactly how #9 records it.

**`PostSchedule` needs no partial index.** A row exists only for an automated post, so
the table is already the sparse subset a `WHERE nextPollAfter IS NOT NULL` predicate
would have carved out of `Post`. Do lower `fillfactor` to ~70-80: these rows churn on
every poll (§5.5.a). Its `post` relation is genuinely traversed — the scheduler claims
schedules and needs the post's `platform` and `platformPostId` to make the call, so this
is the one join in the hot path that is earned rather than tolerated.

**Three rungs of one ordered enum**, each able to lower the one above. The third rung is
the *post's* level; it lives on `PostSchedule` only because that is the post's 1:1 side
table for automation state, and `PUT /v1/posts/:id/automation` writes it there.

```
effective(post) = min( user.maxCommentAutomationLevel,
                       composition.commentAutomationLevel ?? REPLY,
                       schedule?.commentAutomationLevel   ?? REPLY )
```

Null means "don't lower", hence the `?? REPLY` — a null rung must be the identity of
`min`, not `OFF`, or an unset override would silently disable the post. Every rung can
only lower, which is what makes the top one a kill switch: no composition or post can
promote itself past what the account is allowed.

**Row existence is a consequence of the effective level, not a fourth input to it.** The
schedule row is materialized when `effective > OFF` and retired when it falls back to
`OFF`, so the two never disagree and `OFF` has exactly one representation: no row. This
is what keeps a composition-level switch meaningful — raising
`Composition.commentAutomationLevel` from `OFF` has to *create* schedule rows for the
posts under it, which it could not do if row existence were itself an independent signal
being read by the same `min`.

The effective value is never stored — that's what makes lowering
`User.maxCommentAutomationLevel` a working kill switch rather than something needing a
sweep across every row.

**Extensions use a shared primary key**, so one-to-one is enforced by the key rather than
by convention, the join is PK-to-PK, and cascade delete is automatic. It guarantees *at
most* one — "exactly one per platform" would need a trigger and isn't wanted, since most
platforms have no extension at all. **`Post` deliberately does not declare these
relations**: the provider's own repository fetches its extension, so adding a platform
never edits the base model.

**The code has two shapes named after each extension, and both stay sparse in storage.**
`InstagramPost`/`YouTubePost` (`@platforms/*/[platform]-post.ts`) extend `Post` at the
TypeScript level — a convenience so response-building code can hand around one merged
object instead of joining `Post` and its extension by hand. What actually persists is
narrower: `ExtensionRow<TEntity, TExtension>` (`@repository/extension-row.ts`) computes
the diff — the extension's own field(s) plus the shared id — so the repository layer
(`InMemoryExtensionRepository`) only ever stores `{ postId, mediaProductType }` /
`{ postId, privacyStatus }`, matching this schema exactly. The wide type is an
application-layer view; the row that hits the table is still the sparse one.

**No `CommentSyncState`.** Cursor and `lastSyncedAt` live on `PostSchedule`. Both are 1:1
with `Post` and both are per-post sync state; two side tables would split one concern for
no gain, and a second `nextPollAfter` would be a drift hazard.

## Indexes deliberately absent

**`Composition` carries no index beyond its primary key.** The listing index
`(userId, createdAt)` would back `GET /v1/compositions`, which returns `501`. Add it with
the endpoint.

**`Comment` carries no index on `status`.** Nothing ever asks "which replies are queued?"
globally — the pipeline asks "which replies are queued *on this post*", and
`(postId, platformCreatedAt)` already narrows that to a handful of rows for `status` to
filter. Indexing it would buy nothing and would stop the terminal write from being a
heap-only update.

**`Post` carries no `accountId` index.** Nothing queries posts by account: the scheduler
claims from `PostSchedule` by `nextPollAfter`, and comments are read by `postId` or
`compositionId`. It went in alongside `status`, which no longer exists.

**`SocialAccount` carries no standalone `userId` index.** The tenant-scoped unique above
already leads with `userId`, and Postgres uses the leftmost prefix of a composite index,
so a separate one would be a second copy of the same B-tree.

## Still open

**`credentialRef` is Instagram-shaped.** One opaque secrets-store id per account assumes
one credential per account. YouTube needs a project-level API key for reads *plus*
per-account OAuth for writes, which is two credentials with different lifetimes and
different rotation. Still one column here. The *interface* already accommodates it —
`ICredentialStore.resolve(accountId, purpose)` in
[3.social-media-integration.md](./3.social-media-integration.md) means the fix is a
`credentialRef` per (account, purpose) inside the store, with no provider method changing.
