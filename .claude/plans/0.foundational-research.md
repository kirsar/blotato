# 0. Blotato take-home: comment system — general plan

## Task brief (verbatim requirements)
Design and partially implement a comment system for a social media scheduling API.
- Retrieve comments for a published post
- Reply to a comment
- Support multiple social platforms
- Expose functionality through a REST API

Deliverables: DB schema, API design, TypeScript code, explanation of major design
decisions. System already supports multiple platforms, expected to support more later.
Requirements intentionally leave details unspecified — document assumptions.

**User direction:** don't just replicate Blotato's real API — design something from
scratch. Use the real API as ground truth for conventions, but use the freedom of a
brand new product to build something covering future scale and resiliency.

**Target stack** (per user): Next.js (frontend, not directly relevant here), NestJS on
the Fastify adapter (backend — see decision 1.5 below), TypeScript, Postgres, deployed
on Heroku, AWS in the mix.

## Scope guardrail (read before writing any code)

This is still a take-home for an interview, reviewed by a person in a limited amount
of time — **not** a production system to actually operate. The Foundational questions
below have gotten appropriately thorough as a *design* discussion, including sections
marked **Full**, but that depth is about reasoning being recorded, not about how much
code gets written. Explicitly:

- **Full/Brief/Mention-only labels describe documentation depth, not code depth.**
  A "Full" category (API Surface, Storage, Security, Compliance) earns a real
  paragraph explaining the reasoning — it does not mean every guard, interceptor,
  RLS policy, and audit table gets built. Most of what's Full-documented should land
  in code as: the right field on the right model, one enforcement point, and a note
  that the rest is designed-but-not-built.
- **Target: a project a reviewer can read in well under an hour.** Roughly bounded to
  a few dozen source files, not hundreds — one module per real concern (comments,
  platforms, jobs, storage), not one per sub-bullet discussed below.
- When a Full-treatment idea (autonomous-agent guardrails, RLS multi-tenancy, full
  audit trail, real webhook signature verification, per-platform-per-account rate
  limiting) would take real code to do properly, the default is: **document it as
  designed, stub or skip the implementation**. Say so plainly where it's decided — in
  the relevant implementation-plan file itself (as already modeled in
  [1.overall-architecture.md](./1.overall-architecture.md)'s "this module list is the
  ceiling, not a commitment..." note). Better to have 3-4 things fully working and
  well-explained than 15 things half-built.
- Concretely, from the "Open decision points" below: lean toward the smallest
  implementation that still demonstrates the two or three ideas worth demonstrating
  (currently pointing at: the async job runner, the capability registry, and
  idempotency) — not every observation discussed in 0.current-api-overview.md or every
  Foundational-questions category at once.

## Scope of the implementation

**Decided first, because everything downstream is conditional on it.** The statistical
inputs, the capacity figures, and the entire rate-limit analysis only make sense once
this tier is chosen — tier 1 has no standing poll load to size, and tier 3 multiplies
it by every post an account publishes rather than the opted-in subset.

Three tiers of retrieval/management scope, increasing in automation:
1. **One-shot processing** — an API to track posts exists; a human selects a post,
   and the system fetches and processes its comments once, on demand.
2. **Periodic, opt-in automation** — a human turns automation on for a composition,
   after which the system fetches its comments on an adaptive schedule and handles them
   as far as the account's level permits, for a given retention window, with opt-out.
3. **Fully automated, account-wide** — every post created for an account is
   automatically tracked and managed, with no human selection step at all.

**Target: 2.** Matches the literal task ask (retrieve comments for a post) while
still supporting the ongoing/autonomous-reply direction (§4) for posts a human has
opted in — without paying tier 3's cost of blanket-watching every post regardless of
demand.

Per-platform bulk-fetch capability and the webhook/batching levers that follow from
this choice are in [0.capacity-planning.md](./0.capacity-planning.md) §5.

### What this table is actually saying

**Nothing in this system is capacity-bound on our own infrastructure.** Rows 16 through
20 all sit one to two orders of magnitude below a single instance's limits. Row 23 is
the consequence: 3 instances per service, for surviving a failure with headroom, and
for no other reason. Any per-service capacity derivation in §1.4 that concludes
otherwise is stale.

**The binding constraint is the platform quota, and it is the reason the polling design
matters.** Row 9 is not merely expensive, it is ~22x over what Meta permits (row 12), so
flat polling was never available. Row 10 is what makes the design legal, and row 11 is
what gives it margin. That is the single most load-bearing decision in this plan.

**Two inputs are locked rather than scaled, and this is deliberate.** Rows 3 and 4
describe audience behavior and our own filter. Neither has a reason to grow with
customer count, and compounding growth into them inflates every downstream figure by
roughly 25x.

**Row 15 is a real blocker, not a rounding problem.** YouTube exceeds its daily project
quota on post arrival alone, before any poll interval is chosen. It is gated on a Google
quota audit, which is a business process rather than an engineering lever, so platform
onboarding needs a feasibility gate alongside the capability registry (§3.1, §8.1).

**The two most consequential unsourced numbers** are the ~30% daily-active fraction and
the ~50% share of the Meta pool available to comments, both inside row 12. Together they
swing row 13 between ~20% and ~64%. Only production telemetry settles them — Meta
returns `X-App-Usage` as a percentage of the live limit, which lets the real pool be
back-calculated rather than estimated.

## Foundational questions

Recorded as lightweight decision records — these double as "explanation of major
design decisions" material for the final deliverable. Depth per category is
deliberately uneven: some are marked **Full** (load-bearing, full treatment),
**Brief**, or **Mention-only** (flagged, not built out) per explicit scoping calls.
Implementation detail for each category lives in its linked file above, not here.

### 1. General

**1.1 Should we store posts and comments on our own system, or fetch/proxy live from
the platform each time?**
Recommendation: **Yes, store both** — not an arbitrary choice, it falls out of
requirements and decisions already made:
1. The literal task requirement — "retrieve comments for a published post" is a
   standalone REST capability (`GET /comments`); without a store, there's nothing for
   it to return without live-proxying every read, which defeats pagination, cross-
   platform querying, and the REST API this design is for.
2. The async pipeline (fetch → generate → post, 1.4/§4) needs durable state — a
   crash or a failed AI call with nothing written loses the comment silently: no
   retry, no record it ever needed a reply.
3. Manual/human-review mode ships first (§4.3) — a human reviewing a generated reply
   needs something durable and queryable, not request-scoped memory.
4. AI-produced replies (§5.1) must be persisted the instant they're generated — the
   provider call is the expensive, non-repeatable part; losing the result after a
   successful call means paying for it again, not just retrying a cheap write.

Concrete gap this surfaces: `Post` (5.storage.md) currently has no content/caption
field — needed for reply-generation context, captured once at ingestion (not
re-fetched live at generation-time, which would be an uncounted extra platform call
unless the comment-listing response already embeds it — verify per platform).

**1.2 Should clients get a review step before a generated reply posts?**
No — a client-facing review UI is out of scope (Scope guardrail), and §4's direction is
full autonomy. The ordered `maxCommentAutomationLevel` (§4.2) still models `draft` as the
staged-rollout step a future review surface would hang off, but that level is the one
thing this deliverable doesn't build. `collect` and `reply` both ship, which covers
reading comments and replying by hand as well as the fully automated path.

**1.2.a Is a "post" one platform, or one authored piece published to N platforms?**
**Both, modelled explicitly: `Composition` 1:N `Post`.**

**Definitions, used consistently from here on and in every sibling file:**

| Term | Means | Example |
|---|---|---|
| **`Composition`** | one thing the user authored, regardless of where it goes | the caption they typed once |
| **`Post`** | one published post on one platform, with its own `platformPostId`, status, and polling schedule | that caption as it exists on Instagram |

`Post` deliberately stays at the **platform level**, because that is what every
external vocabulary already means by the word: the platforms themselves,
`platformPostId`, the comments-per-post engagement benchmarks, and Blotato's own
`GET /v2/comments?postId=`. Naming the composition `Post` would put this design in
conflict with all four at once. Previously one word covered both levels, which broke
three things:

- **Nothing could answer "comments on the thing I wrote."** A composition fanned out
  to four platforms had four unlinked ids. Now `?compositionId=` aggregates across all
  its `Post`s, each item tagged with its platform, while `?postId=` keeps its existing
  meaning and narrows to one. Replies always target a `Post`, since a reply goes to
  exactly one platform. The new capability is a new parameter, not a redefinition of
  an existing one.
- **`posts/month` (`#2`) was ambiguous by the average fan-out.** Resolved: **`#2`
  counts `Post`s**, which is what the comments-per-post benchmarks measure and what
  polling load scales with. Blotato has no composition concept, so its own figures
  already count this way.
- **Reply context is per-platform.** Captions differ across platforms for length and
  hashtags, so the caption feeding reply generation lives on `Post.content`, with
  `Composition.content` as the authored original and fallback. This closes §1.1's
  flagged missing-caption gap.

Blotato's real API is flat here — cross-posting is N calls to `POST /posts` — so the
composition layer is a deliberate addition, while `Post` keeps the meaning their
integrators already rely on. Schema: [5.storage.md](./5.storage.md).

**1.3 Will we support multiple social networks, and multiple agentic platforms —
including bring-your-own-agent?**
Yes, and yes. Multiple social networks: the literal task requirement, realized via the
capability registry + `ICommentProvider` interface (§3.1) — onboarding platform N+1 is
a scaffold, not a rewrite (§8.1). Multiple agentic platforms, including a client's own
agent: already structural, not a future add-on — agent-authored replies go through the
same `POST /comments` path as a human reply (§4.1), scoped by a distinct agent API key
that is scoped and separately revocable (§7.1, §7.4). **This is the one case that would
justify typing keys by caller kind** — an external machine caller hits the same endpoint
a human would, so the code path can't distinguish them. It is designed, not built
(§4.1). A
client's own agent, given a scoped agent key, can call the same REST API directly — we
don't need to run or integrate their agent ourselves, only accept its output through
the same guardrail-gated path any agent goes through (§4.2).

**1.4 Logical services** — six logical roles, five physical services. Scheduler and
Comment Retriever merge into one worker; Webhook Delivery is designed but not built.

| Logical role | One line | Physical service |
|---|---|---|
| API Service | serves our clients from our DB; turn automation on/off per composition | **API service** |
| Scheduler | picks which posts are due for a comment refresh | **Scheduler-Retriever** |
| Comment Retriever | fetches those comments from the platform | **Scheduler-Retriever** |
| Content Generator | decides which comments deserve a reply, and writes it | **Content Generator** |
| Reply Publisher | delivers approved replies to the platform | **Reply Publisher** |
| Webhook Delivery | notifies *our customers* that a comment or reply landed | **Webhook Delivery** ⛔ out of scope as of now |

**They are separate processes because their failure modes are**, not for tidiness:
each blocks on a different external dependency with its own rate-limit and backoff
semantics — platform reads, an AI provider, platform writes, customer endpoints — so
colocating any two lets one stall the other. They coordinate only through Postgres
status transitions, never direct calls, which is also why no service mesh or gateway
is needed (§1.6).

**Every instance count in this plan is a redundancy decision, not a capacity one.** No
service exceeds one instance's throughput at the 2-year figures; 3 per service is the
baseline for surviving a failure with headroom.

Per-service **Logic, Load, Capacity, Host, Scale**: **[0.services.md](./0.services.md)**.

**1.5 Fastify or NestJS — for future enterprise growth and dev-experience continuity
with Next.js?**
**Overruled: NestJS on the Fastify adapter (`@nestjs/platform-fastify`)**, not plain
Fastify. Original recommendation was plain Fastify (structural benefits reasoned as
achievable by convention, without framework lock-in) — overruled with better
reasoning: Nest gives modules/DI/controllers/guards/interceptors/validation/OpenAPI as
first-class primitives, Fastify still supplies the HTTP layer underneath via Nest's
official adapter (no throughput tradeoff), the domain has enough real complexity
(multi-platform providers, agentic guardrails, multi-tenancy, an async submit-and-poll
job workflow) that architectural structure matters more than hand-rolling it by
convention, and `@nestjs/swagger` gives first-class OpenAPI generation — directly
useful for the API design deliverable itself. This also strengthens decision point 2
(in-memory vs real DB): Nest's DI tokens make swapping in-memory repositories for
Prisma-backed ones a binding change, not a consumer-facing one. Module layout is in
[1.overall-architecture.md](./1.overall-architecture.md); the Fermi estimate is above;
monolith-vs-microservices reasoning is 1.4.

**1.6 Heroku, EC2, or EKS for hosting?**
Recommendation: **Heroku** — matches the target stack, and is genuinely right-sized,
not just convenient. EC2 trades Heroku's convenience for full infra control, justified
only once Heroku's concrete limits (30s request timeout, connection caps — detailed
below) are actually being hit. EKS is the infrastructure a genuine microservices split
would want (independent scaling/deployment per service); nothing about the modular
monolith (1.4) or the Fermi estimate justifies that operational overhead now — Heroku's
Procfile process types already scale each of the 4 services independently (3+ instances
each, redundancy baseline — see 1.4), and since they coordinate only through Postgres
status transitions, not
direct service-to-service calls, there's no inter-service traffic for Kubernetes-grade
orchestration to manage in the first place. Detail + concrete Heroku limits:
[1.overall-architecture.md](./1.overall-architecture.md).

**Do we pay for these instances 24/7, or can this flex for rush hours?** 24/7, by
default — Heroku dynos bill continuously while scaled up; they don't scale to zero,
and native autoscaling is a Performance-tier, web-dyno-only feature (response-time
triggered), not available for worker dynos at all. This is less wasteful than it
sounds here: the Fermi ceiling figures throughout §1.4 are already worst-case peak
assumptions ("every post saturates," an explicit upper bound), so flat 24/7
provisioning at those counts already covers rush-hour peaks without needing dynamic
autoscaling — the cost tradeoff is paying for peak capacity at off-peak times too, not
under-provisioning at peak. Recommendation: flat provisioning for this take-home
(simplicity, matches the Scope guardrail); scheduled scaling (Heroku Scheduler,
cutting worker dyno counts during known-low-traffic windows) is the real lever if cost
mattered later — named as the trigger, not built.

**1.7 At what scale do we need a real queue (e.g. SQS) instead of DB-as-queue
polling?**
Not at this plan's target scale — the actual polling load, summed across all three
pollers' Capacity figures: Scheduler-Retriever ~430/sec ÷ ~130/batch ≈ 3
claim-queries/sec; Content Generator ~49 calls/sec, one assembly query each ≈ 49/sec;
Reply Publisher ~49/sec ÷ ~50/batch ≈ 1 claim-query/sec. **Total ~53 polling
queries/sec**, well under one CPU-core-second/sec of Postgres time at ~5-20ms/query —
a rounding error against one instance's budget, and below the payload traffic (comment
upserts, API reads) sized in 5.6. That grows roughly linearly with load, so the
quantitative trigger now sits **~20-30x beyond this plan's 2-year target** rather than
~10x, since the corrected inputs cut polling load by ~3x. At that distance the
quantitative argument stops being useful, and the case rests entirely on three
qualitative triggers instead: multiple independent consumers needing to fan out from
one event (today one consumer claims one row, no fan-out need), or delivery needing to
cross a process boundary DB polling can't reach (not true while this stays one
Postgres-backed monolith, §1.10). **The honest summary is that this design will never
outgrow DB-as-queue on throughput** — it will change for a structural reason or not at
all.

**1.8 Do we need to worry about Node's libuv I/O threadpool limits?**
Recommendation: **not at this scale**, and structurally avoided by one deliberate
choice — hashing API keys (7.1) with SHA-256, not bcrypt/argon2, since API keys are
high-entropy random tokens rather than low-entropy human passwords and don't need a
deliberately slow adaptive hash. That removes the one place in this design that would
have stressed the threadpool; network I/O (platform calls, Postgres queries) never
touches it regardless of scale. The broader version of this question — is Node's *CPU*
ever the constraint, not just its threadpool — is 1.11.

**1.9 npm or yarn?**
Recommendation: **npm**. In 2026 npm has closed most of the gap with yarn (workspaces,
faster installs, lockfile v3) and is the zero-extra-tooling default — nothing to
install, nothing for a grader or a new hire to get wrong. Also the path of least
resistance on Heroku (default Node buildpack auto-detects `package-lock.json`). Yarn
Berry is legitimate if Blotato already runs a large yarn monorepo, but absent evidence
of that, npm minimizes friction. (pnpm would arguably beat both, but wasn't offered.)

**1.10 Monorepo or polyrepo for this system?**
Recommendation: **monorepo**, for now. There's exactly one codebase today (the
modular monolith, 1.4) even though it runs as four separately-deployed processes — a
polyrepo split has nothing real to separate along yet, and would only add cross-repo
versioning/release overhead for a single small team moving
fast; a monorepo also keeps the NestJS service, `prisma/schema.prisma`, tests, and
this planning system together, which matters for take-home reviewability too. Trigger
to reconsider: once a specific module genuinely needs independent scaling/deployment
*and* multiple teams are shipping into it on different cadences, two costs start to
bite that a monorepo doesn't solve for free — PR/merge contention between unrelated
teams' changes, and the need for dedicated in-house tooling (a real build-graph tool
like Nx/Turborepo/Bazel for incremental builds/tests and remote caching, rather than
rebuilding everything on every change). Until either is actually happening, that's a
tooling investment for a problem this project doesn't have yet. Detail:
[1.overall-architecture.md](./1.overall-architecture.md).

**1.11 Are there HPC-shaped tasks here where TypeScript/Node performance becomes the
bottleneck?** (The general form of 1.8, which covered only the libuv threadpool.)

**Recommendation: no, and the reason is structural rather than a matter of scale — in
this design every expensive computation belongs to somebody else's CPU.** Model
inference runs at the LLM provider. Comment ranking, search, and storage run at the
platform. What remains on our side is: make an HTTP call, parse the JSON, write a row,
update a status. That is the exact workload profile Node is built for, and the sizing
confirms it — the whole system is I/O-bound with roughly 130 concurrent outbound
connections and ~118 database queries/sec at the 2-year target.

Auditing the design for genuinely CPU-bound work turns up four candidates, and only
one is real:

| Work | Cost at 2-year figures | Verdict |
|---|---|---|
| JSON parsing of comment responses | ~430 responses/sec × ~50 comments ≈ 20 MB/s, ~0.1-0.3ms each | ~10-15% of one core — the largest CPU item, and still not close |
| API-key hashing | SHA-256 per request | negligible by the 1.8 decision |
| Prompt assembly, cursor encoding, payload formatting | string operations | negligible |
| **The low-signal comment filter** | ~195 comments/sec | **depends entirely on how it is built — see below** |

**The filter is the one place this could go wrong, and the plan has not yet decided
it.** Dropping ~75% of comments before the model call is the highest-leverage cost
decision in the pipeline, and its implementation is currently unspecified. Three
options with very different CPU profiles:

- **Heuristics** — length threshold, emoji-only detection, absence of a question mark
  or entity mention. Microseconds per comment. Node handles this without noticing, and
  it is the right starting point.
- **A remote classifier API** — this is I/O, not CPU, so it moves the problem into the
  same bucket as everything else. Costs money and latency, not cores.
- **A local ML model** (ONNX, a small transformer) — **this is the case where Node
  genuinely becomes the wrong host.** Inference is sustained CPU work on the main
  thread, and at ~195 comments/sec it would stall the event loop badly. If the filter
  ever goes this way, it does not belong in the Node process.

**The Node-specific risk is latency variance, not throughput.** A single synchronous
`JSON.parse` of an oversized payload blocks every other in-flight request on that
instance — the failure shows up as p99 latency, not as CPU saturation. The mitigation
is bounding payload size rather than adding cores, and the 500-comment page cap
(Statistical inputs A) already does that. Worth noting the cap earns its keep twice:
once as a pagination bound and once as an event-loop guard.

**If a real CPU-bound need did appear**, the escape hatches in order of cost are
`worker_threads` for parallel work inside the same process, a native addon for a hot
inner loop, or a separate small service in another language reached over HTTP. None of
those is a rewrite, which is the actual point: the modular boundaries (1.4) mean a CPU
problem would be contained to one worker rather than forcing a language decision on
the whole system.

### 2. API Surface — Full

**2.1 Build this as a REST API, or as an MCP server for agent clients to call?**
Recommendation: **REST, with MCP as an optional thin adapter, not an alternative
architecture.** The brief mandates REST, and Blotato's own product answers this the
same way structurally: one backend (`backend.blotato.com/v2`) and a *separate* MCP
server (`mcp.blotato.com/mcp`) that almost certainly proxies into that same backend
rather than reimplementing business logic — MCP is a presentation-layer concern, not a
domain-layer one. A `CommentService` owning fetch/reply/validation logic, with REST as
a thin translation on top, means an MCP tool layer (`list_comments`,
`reply_to_comment`) is a same-day addition later, not a fork of the design.

**2.2 REST or GraphQL for a B2B-exposed API in 2026?**
Recommendation: **REST**. For an API consumed by external developers and no-code
automation platforms (Blotato explicitly targets n8n, Make, MCP clients), REST/OpenAPI
wins on ecosystem fit: HTTP caching, per-endpoint rate limiting, trivial API-key auth —
and automation platforms build typed nodes against discrete REST operations, not
arbitrary GraphQL queries. GraphQL earns its complexity for flexible, view-driven
querying (one frontend, many screens); that's not this API's consumer. Endpoint table
is in [2.api-surface.md](./2.api-surface.md).

referenced here, not duplicated.)*

**3.1** How do we abstract per-platform differences? → `ICommentProvider` interface +
capability registry (`supportsComments`/`supportsDelete`/`maxReplyDepth`/

**3.2** Sync strategy — webhook vs polling? → Hybrid: `CommentSyncState` (cursor per

### 4. Agentic Integration (to produce comments) — Brief, aimed at "fully autonomous,
staged rollout"

Per your answer: target is **fully autonomous agent replies** as the long-term goal
("this is the future"), reached progressively rather than built all at once now — so
the design needs to leave room for that ceiling without requiring it on day one.

**4.1** Does agent-generated reply text go through the same `POST /comments` path as a
human-authored reply, or a separate one? Recommendation: **same endpoint/schema** — the
domain shouldn't care who produced the text, only that the right guardrails ran before
it left `queued`. One code path, not two.

**No `actorType` field on `Comment` or `ApiKey`.** In the flow this system runs (§0
tier 2, autonomous generation), the Content Generator is our own worker: it reads and
writes Postgres and never presents an API key, so a reply's provenance follows from
*which code path wrote it*, not from a credential. `isAuthor` already separates our
replies from audience comments, and the guardrail gate is `maxCommentAutomationLevel` (4.2), not
actor identity. If human/agent provenance is needed later — for compliance disclosure,
or once BYO-agent (1.3) is real — the cheaper form is `createdByApiKeyId` on `Comment`,
which says *which* key rather than merely what kind, and is what revocation forensics
would actually want.

**4.2** What guardrails need to live *in the API*, not just at the agent layer, before
an unattended reply can post? Recommendation: `User.maxCommentAutomationLevel`
(`off | collect | draft | reply`, ordered) caps how far down the pipeline any
composition may run — `draft` means a generated reply needs a human promotion step,
`reply` means it may send. Plus a required `guardrailCheck` record (moderation result,
model id, confidence) attached before promotion — enforced server-side so a compromised
or misconfigured agent can't bypass it by calling the endpoint directly. The ceiling is
a *grant*, evaluated at use time rather than stored per composition, so lowering it
stops everything on the next poll (2.api-surface.md).

**4.3** How do we let scope expand without a rewrite? Recommendation: model automation
depth as that ordered ceiling (4.2), not a hardcoded pick. `collect` ships first — the
smallest surface that's still genuinely useful and testable, since the caller reads
comments and replies by hand — and `reply` is a config change once the guardrail
machinery is trusted, not a separate implementation.

**4.4** Non-determinism → directly shapes Storage (5.1): a generated reply can't be
regenerated identically, so it has to be persisted the moment it's produced, not
buffered or delayed — losing it after a successful provider call wastes that call.

**4.5** The Content Generator service is the system's tightest bottleneck — bound by
the external provider's rate/cost limits, not our own infra, and binding immediately
rather than something growth would trigger later (see 1.4). Recommendation: split it
out as its own independently-
scaled worker pool from day one (own concurrency/rate-limit config, own provider-key
rotation) — not a separate deployable/codebase, just its own scaling knob within the
monolith (see 1.4, 1.10). A queue only buffers bursts, it doesn't raise sustainable
throughput; since the provider ceiling can't be exceeded by adding workers, fix
**demand** (what enters the queue) before **supply** (processing capacity), in order
of impact: (1) don't generate a reply for every comment — filter low-signal ones (e.g.
"👍"-type) before the LLM call at all, cutting volume before it hits the limit; (2)
batch multiple comments per LLM call where context allows; (3) pool multiple provider
API keys/orgs to raise the ceiling; (4) accept latency — queue replies rather than
treating "immediate" as a requirement.
Also reconsider the 50%/75% reply-rate targets (Capacity planning) as *policy
aspirations*, not guarantees — actual achievable reply rate may be capped by this
service's real throughput, not by the automation ceiling.

### 5. Storage — Full (per your flag: interconnected with Agentic, resilience over
non-deterministic engines)

**5.1** What does "resilient over a non-deterministic engine" concretely require?
Recommendation: **persist AI-produced replies the instant they're generated.** The
provider call is the expensive, non-repeatable part — a reply is written to `Comment`
at `DRAFT` status as soon as the call returns, not buffered or delayed; losing it
afterward means paying for that call again, not just retrying a cheap write. This is a
durability requirement on the write path, not a separate logging concern — the schema
consequence of 4.2/4.4 is the `DRAFT` status itself, nothing beyond it. See
[5.storage.md](./5.storage.md) for the finalized Prisma schema.

**5.2** Does an autonomous pipeline need a state distinct from today's `QUEUED`
(which currently means "confirmed, about to send")? Recommendation: **yes** — add
`DRAFT` ahead of `QUEUED` so agent-generated replies can exist without being live-
bound; a promotion step (human click, or the `autonomous` config path) moves
`DRAFT -> QUEUED`.

**5.3** Postgres vs alternatives for this workload? Recommendation: **Postgres**
remains right — matches the stack, gives strong consistency for the "comments table
doubles as the reply queue" pattern (5.1), and the workload's shape (relational,
status-driven, indexed lookups) doesn't need a different engine. Sized against the
Fermi estimate above.

**5.4** Per-tenant storage isolation? → see 7.2; Storage and Security share this
boundary rather than each owning a separate answer.

**5.5** How much total data does this system actually accumulate — disk size, not
throughput?

**This is a stock question, so it is derived from monthly totals, not from per-second
rates.** Rows resident = monthly volume × (45-day retention ÷ 30-day month) = monthly
volume × 1.5. Every input is a direct lookup from [0.capacity-planning.md](./0.capacity-planning.md) block 1. (5.6
below is the matching *flow* question, and that one legitimately uses per-second
rates.)

| Table | Monthly volume | × 1.5 retention | Rows resident | Est. size/row | Total size |
|---|---|---|---|---|---|
| `Composition` | not estimated | | ≤ `Post` count | ~400B | negligible |
| `Post` (per-platform, §1.2.a) | 10^7 | | ~1.5×10^7 | ~900B | ~14 GB |
| `Comment` (inbound, ingested) | 5×10^8 | | ~7.5×10^8 | **~800B** | ~600 GB |
| `Comment` (our replies) | 1.25×10^8 | | ~1.9×10^8 | **~800B** | ~152 GB |
| **Total** | | | **~9.6×10^8 rows** | | **~0.77 TB** |

Per-row sizes are now derived rather than guessed — see
[0.capacity-planning.md](./0.capacity-planning.md) §D, which breaks the ~800B into
~276B of identifiers, ~105B of text at a measured ~80-character mean, ~30B of Postgres
overhead, and **~355B of index entries**. A flat ~500B/row guess understates the total
by roughly 60%, because it misses the index share.

Three results worth keeping:

- **Indexes are ~45% of the `Comment` footprint**, not the text. That is the
  counterintuitive one, and the actionable one: a *full* index on this table costs ~64 GB
  at these figures, which is why the idempotency index is partial — only client-supplied
  outbound replies carry a key, so it covers ~1 GB instead (5.storage.md).
- **Text is the small part.** Real comments are short — measured medians run ~38-50
  characters — so a comment row is mostly keys and index entries. Sizing from the
  *maximum* comment length instead would have overstated storage by more than an order
  of magnitude.
- **~0.77 TB is an ordinary single-instance Postgres database**, which is what matters —
  and the reason 5.6 below stays short. `Post` remains ~1.5 orders of magnitude smaller
  than the comment tables despite being the entity everything hangs off.

**5.5.a Should scheduling state be updated in place, or written as an append-only log
with latest-timestamp-wins and frequent cleanup?** **Update in place.** The append-only
framing assumes an in-place mutation we'd be avoiding, and Postgres has none: MVCC
already writes a new tuple version on every update and marks the old one dead. A log
doesn't avoid that write, it just moves cleanup from autovacuum to our own `DELETE`,
which produces dead tuples of its own.

The real cost is elsewhere and a log wouldn't fix it either: `nextPollAfter` is the
scheduler's claim index and changes every poll, which defeats **HOT** (heap-only tuple)
updates and forces a btree write each time. And a log actively damages the hot path —
"which posts are due" is one indexed range scan today, but against a log it becomes
latest-row-per-post across ~1.5×10^7 rows on every tick. That trades a cheap constant
read for an expensive one to make an already-cheap write marginally cheaper. At ~430
scheduling updates/sec none of this binds anyway; Postgres sustains orders of magnitude
more.

Three refinements worth taking on structural grounds rather than need: a narrow
`PostSchedule` side table so an interval update doesn't rewrite the whole `Post` tuple,
and a lowered `fillfactor` (~70-80) so pages keep room for new tuple versions. Note the
side table also **subsumes a partial index** — a row exists only for an automated post,
so the table is already the sparse subset a `WHERE nextPollAfter IS NOT NULL` index
would have carved out. The two were alternatives, not complements.

Append-only *is* right for a different thing: a poll-attempt log recording what each
poll returned, its latency, and errors. That is genuinely write-once, never read on the
hot path, and time-partitioned so cleanup is a partition drop. Separate table, separate
job, no effect on scheduling. Not built (§10.1).

**5.6** At what point does a single Postgres instance stop being enough? Two numbers
check that, not one: **query rate** (round-trips and planning — what batching fixes)
and **row-level write throughput** (WAL and index bytes — what batching doesn't, since
the same data hits disk regardless of statement count). Scheduler-Retriever and Reply
Publisher flush on a time/size micro-batch trigger (~200ms or ~100/~50 results,
whichever first), which bounds the data-loss window rather than waiting for a full
claim round.

| Source | Operation | Query rate | Rows/sec |
|---|---|---|---|
| Scheduler-Retriever | Batch upsert `Comment` + `CommentSyncState` (3 instances, time-triggered) | ~15/sec | ~195 |
| Content Generator | Insert `Comment` (reply, per LLM call) | ~49/sec | ~49 |
| Reply Publisher | Batch update `Comment`.status (3 instances, size-triggered) | ~1/sec | ~49 |
| **Writes** | | **~65/sec** | **~293/sec** |
| Reads (API + 3 claim/assembly queries) | | ~53/sec | — |
| **Grand total** | | **~118/sec** | **~293/sec** |

**Answer: nowhere near, and the question has no interesting answer at the 2-year
target.** ~118 queries/sec and ~293 write rows/sec against ~0.77 TB is an unremarkable
workload for a single well-indexed instance — roughly two orders of magnitude below
where a tuned Postgres starts to strain.

Two levers are worth naming; the rest are not.

1. **Vertical** — bigger instance, tuned autovacuum and indexes, and relaxed
   `synchronous_commit` for this data specifically, since comments are re-fetchable
   from the platform and async commit's small data-loss window is an acceptable trade.
   Cheapest, and the only one likely ever needed.
2. **Native time-partitioning on `Comment`** — worth doing regardless of scale, not as
   a capacity lever but because it turns retention cleanup into an instant partition
   drop instead of row-by-row `DELETE` competing with foreground writes. This is the
   one item here that should probably happen anyway.

**Explicitly dropped from this section**: horizontal sharding by account, managed
distributed Postgres (Citus), and a Kafka/Kinesis buffer in front of ingestion. All
three were sized against write volume that does not exist at these inputs. Recorded
here as considered-and-rejected so they are not re-proposed, and so it is clear the
omission is a decision rather than an oversight.

### 6. Compliance & Data Retention — Full

**6.1** We store third-party (audience) PII — comment `text` + `platformAccountId` — and
platforms can require deletion. Recommendation: honor platform-originated delete/
deauth webhooks by cascading to `status = DELETED` on our copy, not leaving stale PII.

**6.2** Retention policy. Recommendation: don't hardcode Blotato's real "45 days" as a
universal truth; make retention a configurable policy per user with a scheduled
cleanup job — an ops/business decision, not something baked into the schema.

**6.3** Right-to-erasure for a commenting *audience member* who isn't our direct
customer. Recommendation: since `platformAccountId`/`text` are the only PII captured (per
0.current-api-overview.md #9), a deletion request just nulls those two fields on matching
`Comment` rows — one table, one statement, which is why no separate author table exists.
Worth
flagging explicitly: Blotato's public docs don't mention GDPR handling at all — this
is a real gap, not an assumption to skip past.

**6.4** Agent-authored content compliance. What this design actually captures is the
`DRAFT`/`QUEUED`/`POSTED` lifecycle (5.1/5.2) — proof of *what* got posted and *when*,
not a full trail of *why* the model produced it. A deeper compliance/explainability
record (prompt version, guardrail confidence, decision rationale per reply) is a real
gap for a production system, explicitly descoped here rather than built.

### 7. Security & Multi-tenancy — Full

**7.0 What is the tenant?** Answered first, since 7.1-7.4, `maxCommentAutomationLevel` (4.2), and
retention (6.2) all scope to it.
Recommendation: **`User` is the tenant**, owning API keys, connected accounts, and
per-tenant policy. This matches Blotato's own shape — `GET /users/me/accounts` returns
a list, so one user already holds many accounts across many platforms, including
several on the same platform.

**No `Workspace` layer above the account holder.** One would earn its place for two
cases — several people sharing one set of accounts (team), or one person owning several
*isolated* client groups (agency) — but both need a membership model, and without one
the layer is a renamed `User` with identical cardinality and no members: cost with no
capability. Multi-seat access is a genuine production gap, named here rather than
half-built (Scope guardrail).

**Load-bearing invariant: an account belongs to exactly one tenant** — that's what
makes anything keyed by account single-tenant, which §1.4's Content Generator relies on
when it groups work by account. Remaining gaps: capacity planning treats MAU and
connected accounts as one number (`#1`), which the account list shows they aren't; and
`maxCommentAutomationLevel` sits on the tenant, so a user running several brands can't vary it
per account — the account is probably its more defensible home, since that's where both
reputational exposure and platform quota sit.

**7.1** Auth model for the REST API. Recommendation: API key per user (mirrors
Blotato's real `blotato-api-key`), hashed at rest, scoped to that user; agent/MCP
callers get their own scoped, separately revocable keys (§7.4). Keys are **not** typed
by caller kind, since our own generator never presents a key at all (§4.1). Typing them
becomes justified only if BYO-agent (1.3) ships.

**7.2** Multi-tenancy boundary. Recommendation: every table carries (or reaches, via
`accountId -> SocialAccount -> user`) a `userId`; enforced in every repository query,
not just at the application layer — Postgres row-level security as defense-in-depth
given this stores third-party PII across tenants. `Comment` and `Post` carry `userId`
denormalized rather than reaching it through a join, so an RLS policy on the hottest
tables doesn't join on every row check (5.storage.md).

**7.3** OAuth credential storage for connected social accounts. Recommendation: never
co-locate platform OAuth tokens with comment data; reference a secrets store (AWS
Secrets Manager, given AWS is already in the stack) by id, kept fully out of the
comments domain model.

**7.4** Agent key blast radius, given 4's autonomous-replies goal. Recommendation:
scoped, revocable agent keys; the `maxCommentAutomationLevel` (4.2) enforced server-side so a
compromised agent key is bounded by the account's cap, not just client-side trust.

### 8. AI Dev Tooling & Onboarding — Brief

**8.1** What makes onboarding platform N+1 fast for a developer (or an AI agent doing
the work)? Recommendation: since all platform-specific logic is already isolated
behind `ICommentProvider` + one capability-registry entry (0.current-api-overview.md #1), the
remaining friction is boilerplate — a scaffold generator (plausibly a Claude Code
Skill: `/onboard-platform <name>`) that stubs the provider file, registry entry, and
test fixtures from a template is mostly templating, not design work.

**8.2** Same question for onboarding a *new agentic platform* (a new LLM/agent
framework calling our API). Recommendation: keep agent-facing tool definitions thin
and declarative (a schema/manifest, not new business logic) — consistent with 2.1's
"MCP as thin adapter" call — so adding one is "write a manifest," not new code paths.

**8.3** Should the scaffold tooling itself be a real deliverable, or documented only?
Recommendation: **document the convention clearly** (directory layout, the one
interface + one registry entry pattern) as the actual deliverable; mention a scaffold
skill as a named fast-follow rather than building tooling-for-tooling's-sake inside
the take-home.

### 9. Testing — Brief (test pyramid required: E2E over localhost + many unit tests)

**9.1** Pyramid shape. Recommendation: many **unit tests** (`CommentService`
validation, capability-registry rules, `ReplyJobRunner` state transitions, per-
provider normalization mapping) against mock providers/in-memory repos; a handful of
**integration tests** (supertest against the Nest/Fastify app, in-memory repos); at
least **one true E2E test** that boots the real server on localhost and hits it over
real HTTP — proving the whole wire path (routing, validation, serialization), not
just a handler function called directly.

**9.2** What's mocked at each layer. Recommendation: even the E2E test uses in-memory
repos + mock providers (per decision point 2 below) rather than a real DB/real
platform call — determinism and zero external dependencies matter more than "fully
real" for a take-home. State this as a documented tradeoff, not a hidden shortcut.

**9.3** How do you test something whose output isn't reproducible (4's agentic
piece)? Recommendation: test the **guardrail/state-machine logic** deterministically
(given a fixed mock "agent output," does `DRAFT -> QUEUED` promotion behave correctly)
— not the LLM's actual output quality, which is an eval concern, explicitly out of
scope for unit tests.

### 10. Observability & Operations — Mention-only

**10.1** Minimum viable observability for a take-home: structured logs on the job
runner (attempt count, failure reason) and a `/health` endpoint. Full metrics/
alerting/SLOs are named as future work, not built — flagged so it's clear this was a
scope decision, not an oversight.

### 11. Versioning & Platform Onboarding — Mention-only

**11.1** Keep the `/v1` prefix from day one so a breaking `v2` has somewhere to go
without disrupting integrators — mirrors Blotato's own real `/v2` implying a `/v1`
existed once. The onboarding playbook itself is the capability-registry pattern
(3.1, 8.1) — cross-referenced here rather than repeated.

## Open decision points (resolved)
1. **Job runner: real code.** The DB-polling worker pattern (`FOR UPDATE SKIP LOCKED`,
   status/attemptCount/backoff) is implemented, not just documented — one of the two or
   three ideas the Scope guardrail names as worth demonstrating in full.
2. **Persistence: in-memory repositories**, DI-token-swappable (1.5). The Prisma schema
   in [5.storage.md](./5.storage.md) stays a design artifact, not wired to a live
   Postgres/SQLite instance.
3. **Providers built as real (mock) code: Instagram, YouTube, and a synthetic "Platform
   Emulator."** Facebook drops out of the *built* set — stays in the capability registry
   as documented-only (0.current-api-overview.md: Facebook does support comments in
   reality, it's just not one of the three implemented here). Twitter stays registry-only
   as explicitly unsupported.

   **The pair is chosen to stress the interface, not to look plausible.** Instagram and
   YouTube diverge on nearly every axis `ICommentProvider` and the rate limiter have to
   abstract, so an interface that fits both has a real chance of fitting platform N+1:

   | Axis | Instagram | YouTube |
   |---|---|---|
   | Budget unit | counts **calls** | **weighted units per operation** — list costs 1, insert costs 50, so 10,000/day is 10,000 reads *or* 200 writes |
   | Budget scope | pooled, scales with daily active users | **fixed per project**, doesn't scale with users at all |
   | Read vs write limits | separate — 60 writes/hr inside a 200 calls/hr read budget | one pooled budget both draw on at different rates |
   | Thread depth | flat | genuinely nested |
   | Max comment length | 2,200 | 10,000 |
   | Auth artifact | page/user token **per account** | project key **plus** OAuth for writes |

   The first row is the one that matters most: a rate limiter shaped as `consume(1)` is
   simply wrong for YouTube, so the provider must declare a per-operation cost. Instagram
   paired with LinkedIn or Facebook would never surface that, which is why LinkedIn was
   dropped — its rate limits are also unpublished (0.capacity-planning.md §C), so its
   capability row would have been guesswork.

   **The Platform Emulator is set to hostile extremes, not a neutral middle** —
   `maxCommentLength` 150 and `maxReplyDepth` 1 — so TikTok's generator-breaking
   constraint is exercised deterministically, with no credentials and no third
   integration.
4. **Idempotency-Key support: real code. `DELETE /v1/comments/:id`: designed, not
   built** — a capability check and a status transition, delivered by the worker the
   same way a reply is, rather than calling a writer synchronously from the web
   process.
