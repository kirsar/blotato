API Service

Serves our own clients from our own DB; no platform calls or polling here.

Logic
Request handler, not a loop — the only service with no queue. Reads hit Postgres directly (no platform fetch on GET). Writes are accepted and queued, never executed inline: POST /comments writes Comment@QUEUED and returns 201 immediately. Owns the automation surface — sets Composition.commentAutomationLevel / a PostSchedule override, and seeds nextPollAfter, which is what puts a post into the Scheduler-Retriever loop at all.
Load
~3.9 posts/sec write-side anchor. Client read volume is unestimated — a known gap, since reads are argued to dominate.
Capacity
Single instance handles low-hundreds to low-thousands req/sec for indexed CRUD — ~4/sec isn't close to it.
Host
Its own process — trivially separate from the three loop-based services.
Scale
3+ replicas from day one, for redundancy, not throughput.
When / how to scale
Scale on observed latency/CPU saturation, not the 4/sec figure. Add replicas behind the reverse proxy (Heroku's router). Stateless, so any replica serves any request.

Scheduler-Retriever

Merges the Scheduler and Comment Retriever roles — one claim cycle serves both once dispatch is concurrent.

Logic
One loop: (1) claim posts whose nextPollAfter has passed via FOR UPDATE SKIP LOCKED; (2) retire posts past the polling window (~14d) or delete data (~45d) instead of re-queueing; (3) fetch incrementally from CommentSyncState's cursor, never a full re-read; (4) reschedule adaptively — per-post interval from observed comment velocity, jittered so co-published posts don't stay phase-aligned.
Load
~430/sec retrieval (post arrival × ~110 polls/lifetime); the 14-day polling window brings this down to ~185/sec. A flat re-poll across the full 45-day window would be ~15,000/sec — ~22x over the platform's effective ceiling.
Capacity
~130 steady-state concurrent connections (430/sec × ~300ms) — well inside one instance's ~1,000 sustainable connections. Capacity needs one instance; dispatch still goes through a bounded-concurrency pool nesting a per-account rate limiter, since the platform quota is the real constraint.
Host
Own process — claim and fetch merged into one pipeline; separate from the API (loop vs. handler) and from Reply Publisher/Content Generator (different external dependency and rate-limit profile).
Scale
3 instances — redundancy baseline, not a capacity figure.
When / how to scale
Binding signal is the platform quota, not our infra — more instances spend the shared pool faster past the ceiling. Remaining levers: webhooks (the only one that buys quota), the 14-day window, and a quota-increase request.

Content Generator

Decides which inbound comments deserve a reply and writes it. Bound by the AI provider's rate/cost limits, not our infra.

Logic
(1) Claim inbound comments with no reply yet via @@index([parentCommentId, isAuthor]); (2) filter low-signal comments (~75% of volume) before spending anything on the provider call; (3) group survivors by (userId, accountId), one call per group, with the platform's maxCommentLength applied as a prompt constraint; (4) persist at status=QUEUED the moment the call returns — DRAFT is out of scope, so there's no promotion step.
Load
~49 reply generations/sec (~195/sec system-wide arrival × 25% reply-eligible). Batching doesn't pay at average volume (~1.07 replies/batch) but stays cheap insurance for bursts.
Capacity
~2.3s/call → ~113 in-flight calls, fits one instance. Cost, not concurrency, is the binding constraint: unbatched replies would run ~$39k-156k/month; prompt caching the per-user preamble cuts that to ~$16k-65k/month.
Host
Own process — different external dependency (AI provider) with its own rate-limit/backoff semantics than the platform-facing services.
Scale
3 instances, redundancy baseline — ~113 in-flight calls fit in one.
When / how to scale
Watch provider 429s/token throttling and reply backlog growth, plus cost per reply (it binds before concurrency). Scale up to the provider's rate ceiling, then: prompt caching first, then tighten the low-signal filter, then pool provider keys, then accept latency.

Reply Publisher

Delivers approved (QUEUED) replies to the platform — the write side of platform integration.

Logic
(1) Select outbound QUEUED comments on the posts this pass claimed; (2) post through the platform provider via a bounded-concurrency pool nesting a per-account rate limiter; (3) record the outcome — POSTED with platformCommentId, or FAILED with an error code; a retryable failure writes nothing, so the row just stays QUEUED until the post next falls due. Writing platformCommentId also makes our own reply an idempotent upsert on the next poll — otherwise a failed status write risks the generator replying to itself.
Load
~49 replies/sec, one HTTP call per reply — most platforms don't accept a batch post.
Capacity
~15 concurrent in-flight calls, trivial for one instance. The real constraint is the platform's write cap (e.g. Instagram: 60 writes/hour/user) — at ~49/sec across ~10^5 accounts that's only ~3% of the cap.
Host
Independent: load is decorrelated from Scheduler-Retriever's, calls block on platform latency/rate limits, and it holds OAuth credentials for every connected account — isolation narrows blast radius.
Scale
3 instances, redundancy baseline — capacity alone needs well under one.
When / how to scale
Watch posting latency/backoff and platform 429s. Add instances up to each platform's own rate ceiling; beyond that, pool app credentials where allowed or accept latency.

Webhook Delivery ⛔ out of scope

Notifies our customers that a comment arrived or a reply posted, so integrators don't have to poll our API. Specified for shape; not built.

Logic
A pure consumer of a WebhookDelivery queue — never reads Comment itself. Producers (Scheduler-Retriever, Reply Publisher) insert delivery rows in the same transaction as their own write, making emission exactly-once by construction. The worker claims QUEUED rows, POSTs the frozen payload with an HMAC signature, and updates status/attempt/backoff.
Load
Bounded above by ~195 comment events/sec + ~49 reply events/sec ≈ ~244 deliveries/sec at full subscription uptake — far lower in practice.
Capacity
Customer endpoints are slower/less predictable than platform APIs (~500ms-2s) — ~244 concurrent in-flight calls, still inside one instance.
Host
Would be independent — it blocks on customer endpoint health, not platform rate limits; colocating it would let one hanging subscriber starve reply posting.
Scale
3 instances if built. Unlike every other service, there's no external ceiling here — it's the one service that genuinely scales by adding capacity.
Why it isn't built
The delivery mechanics match the Reply Publisher's shape, but the destination URL is attacker-controlled and SSRF protection isn't deferrable — a delivery worker without address filtering is a credential-exfiltration path. All-of-it or none-of-it, and the budget didn't cover all of it.
