# 3. Social Media Integration — implementation plan

Decisions and rationale: [0.general-plan.md](./0.general-plan.md) §3. Module wiring,
vertical slicing and the `@PlatformProvider()`/`DiscoveryService` mechanism belong to
[1.overall-architecture.md](./1.overall-architecture.md); per-service behaviour to
[0.services.md](./0.services.md). **This file owns the provider port** — the interfaces
every platform implements, the types crossing that boundary, and the error vocabulary the
workers switch on.

## One class per platform, two interfaces

```ts
interface ICommentReader {
  listComments(post: Post, schedule: PostSchedule): Promise<FetchedPage>;
}

interface ICommentWriter {
  createReply(comment: Comment): Promise<{ platformCommentId: string; platformCreatedAt: Date }>;
  deleteComment(comment: Comment): Promise<void>;
}
```

`InstagramProvider` and `YouTubeProvider` each implement both and are bound to both
tokens. `ProviderRegistry` exposes `reader(platform)` and `writer(platform)` over the same
discovered instance.

**Why two interfaces and not one.** Reads and writes differ in three ways that are already
load-bearing elsewhere, and each one wants the split expressed in the type system rather
than in a comment:

- **Credentials.** Instagram needs one token per connected account; YouTube needs a
  project-level API key for reads *plus* per-account OAuth for writes. Two interfaces give
  the credential store two purposes to resolve against (below).
- **Cost.** A YouTube list is 1 unit and an insert is 50 (`PLATFORMS` in
  [5.storage.md](./5.storage.md)), so the rate limiter cannot be `consume(1)` — the
  operation determines the cost, which means the operation has to be a distinct thing.
- **Blast radius.** In §1.4's split design `worker-retriever` never needs write
  credentials, and separate tokens let its module bind only the reader — enforced by
  wiring rather than trusted. The demo's single pipeline worker calls both, so this one is
  a property of the target topology, not of what ships.

**Why one class implements both anyway.** Base URL, HTTP client, response mapping and
throttle parsing are shared. Two classes per platform would need a shared base class
immediately, which is more structure than one class bound to two tokens. The seam stays
free: when a platform genuinely diverges, that one class splits and no call site changes
(see *Where a platform splits*, below).

**`deleteComment` is a write.** It mutates and needs write credentials, so grouping it
with reads because it isn't a reply would put write authority in the retriever.

**Consequence worth stating: the `web` process holds write credentials.**
`DELETE /v1/comments/:id` is synchronous ([2.api-surface.md](./2.api-surface.md)), so it
calls a writer directly rather than queueing. The isolation claim is about the retriever,
not about the whole system.

## There are no post operations

The port covers comments only. **Writes** are authoring, which is another system's surface
and out of scope end to end. **Reads** look necessary and are not: `InstagramPost.
mediaProductType` and `YouTubePost.privacyStatus` gate whether a post can be polled at
all, so it seems the provider needs a `getPost` to re-check. It doesn't, because the two
gates are answered from two places that already exist.

- **What is known at creation is local.** A Story is never commentable. The Instagram
  provider reads its own `InstagramPost` row — its own module's repository, per the
  slicing rule — and throws `PostUnavailableError { permanent: true }` without spending a
  call. The scheduler retires the post.
- **What changes over time is answered by the fetch itself.** A private video's comments
  are inaccessible, and privacy can flip back at any moment. Attempting the list *is* the
  check: the call fails, the provider normalizes it to
  `PostUnavailableError { permanent: false }`, and the scheduler suspends at the maximum
  interval instead of retiring. A dedicated `getPost` would spend quota to learn what the
  next call reports for free, and would still be stale by the time the list ran.

That is why the permanent/transient distinction lives on the error rather than on a
capability query, and why the two `Post` extensions justify their existence without adding
a port method.

## Types crossing the boundary

**Entities go in.** `listComments` takes the `Post` and its `PostSchedule`; `createReply`
and `deleteComment` take the outbound `Comment`. Nothing is wrapped. A provider reads a
handful of fields off each and ignores the rest, which costs nothing and keeps the call
sites free of assembly code.

Credentials are not parameters — the provider resolves them itself (below). Page size is
not a parameter either: it is a registry constant the provider owns.

`Comment` carries everything a write needs on its own row — `platform`, `accountId`,
`platformPostId`, `platformParentCommentId`, `text`, `platformCommentId` — which is what
makes both writer methods single-argument and keeps the publisher's hot path free of a
join to the parent.

**A narrow type comes back.**

```ts
type FetchedComment =
  Pick<Comment, 'platformAccountId' | 'platformParentCommentId' | 'text' | 'platformCreatedAt'> & {
    platformCommentId: string;  // always set here; nullable on the row until a reply confirms
  };

type FetchedPage = {
  comments: FetchedComment[];
  nextCursor: string | null;    // null = caught up; only meaningful when syncMode is 'cursor'
};
```

**The return cannot be a `Comment`, and the reason is not purism.** A provider lives
outside our id space: it cannot supply `id`, `userId`, `postId`, `compositionId` or
`accountId`; it has no concept of `status`, `errorCode` or the idempotency columns; and it
cannot compute `isAuthor`, which is derived by comparing `platformAccountId` against the
`SocialAccount`. Widening `Comment` to make those optional would weaken the model for
every consumer in order to accommodate one boundary.

The mapper that closes the gap is not ceremony — it is where `isAuthor` gets derived and
our ids get assigned, and that derivation is what stops a re-ingested reply of our own
from being read as fresh audience input ([5.storage.md](./5.storage.md)).

**The `Pick` is deliberate.** Those four fields pass through untouched, and deriving the
port type from the model means renaming one on the row fails the build here rather than
drifting. The two that are not picked are exactly the boundary: `platformCommentId` is
nullable on the row and never null coming back, and everything else is ours.

**`platformParentCommentId` and `platformCreatedAt` are real columns on `Comment`**, not
port-only fields. The first is the platform's parent id, distinct from `parentCommentId`,
which is our cuid — different namespaces, so one column cannot serve both, and holding
both lets ingest defer resolving the parent instead of doing a lookup per comment. The
second is when the comment was written *on the platform*, which is not `createdAt` — that
is when we ingested it. They agree to within a poll interval normally and diverge by hours
after a slow poll, and a caller filtering `?since=` means the platform's clock.

**The platform payload is mapped and discarded.** Nothing raw is persisted; there is no
`platformData` JSONB. A field earns a column by being read, not by arriving.

## Error taxonomy — the provider states a fact, the caller decides

Every provider failure is normalized into one of six errors. The workers switch on the
type and never on the platform, which is the property that keeps platform knowledge inside
the platform module.

| Error | Raised when | Handled by | Outcome |
|---|---|---|---|
| `ThrottledError { resetAt?, retryAfterSec?, usagePct? }` | quota or rate limit refused the call | scheduler / publisher | `resetAt` if given, else `now + retryAfterSec`, else exponential backoff |
| `PostUnavailableError { permanent }` | Story, disabled comments, private video | Scheduler-Retriever | `true` → retire the schedule; `false` → suspend at max interval |
| `CommentGoneError` | the target comment no longer exists upstream | publisher / retriever | mark the row `deleted`; a reply owed to it is terminal |
| `PlatformRejectedError { code, message }` | 4xx we caused — too long, bad depth, malformed | publisher / web | terminal, no retry; `status: failed` with the code recorded |
| `PlatformApiError { httpStatus }` | 5xx, timeout, transport failure | publisher / retriever | retry under the normal backoff |
| `CredentialInvalidError` | token expired, revoked, or scope lost | both | terminal for the whole account, not the row — every call on it will fail identically |

**Only parsing is per-platform.** YouTube signals exhaustion as `quotaExceeded`, Meta puts
usage in `X-App-Usage`, X uses reset headers. Reading that is the one thing a provider
uniquely knows. Choosing the next poll time is a single rule the scheduler applies to the
normalized facts, which is why there is no per-platform scheduler and no `QuotaPolicy`
class yet ([1.overall-architecture.md](./1.overall-architecture.md), Quota handling).

**`CredentialInvalidError` is account-scoped, and nothing currently acts on that.** Every
post on the account will fail the same way, so retrying each one individually burns quota
to relearn one fact. The right response is disabling the account and emitting
`account.credentials.expired`, which lives in the `501` subscriptions surface
([2.api-surface.md](./2.api-surface.md)). Named here so the gap is visible rather than
discovered.

**Validation is the caller's, not the provider's.** `maxCommentLength` and `maxReplyDepth`
are checked in `CommentsService` before a row is written, and `maxCommentLength` again as
a prompt constraint before generation. A provider does not re-check; a slip surfaces as
`PlatformRejectedError` and is terminal.

## Credentials are resolved by purpose

```ts
interface ICredentialStore {
  resolve(accountId: string, purpose: 'read' | 'write'): Promise<Credential>;
}
```

The provider calls this itself rather than receiving a token, so no credential value ever
appears in a signature, a log line, or a queue row — `SocialAccount.credentialRef` holds a
secrets-store id and never a token ([5.storage.md](./5.storage.md) §7.3). The demo binds a
fake store, which keeps the boundary structurally real even though the secret behind it
is not.

**`purpose` is what makes YouTube expressible.** A single `credentialRef` per account is an
Instagram-shaped assumption; YouTube needs a project key for reads and per-account OAuth
for writes — two credentials, two lifetimes, two rotation schedules. Resolving by purpose
means the eventual `credentialRef` per (account, purpose) is a change inside the store and
its schema, not a change to any provider method. This is the open item in
[5.storage.md](./5.storage.md) *Still open*, and this interface is where it lands.

## Pagination: the registry decides, the provider hides it

`syncMode` is a registry constant, and it says which incremental mechanism the platform
actually supports.

- **`cursor`** (Instagram) — forward pagination genuinely captures what is new. The
  provider reads `schedule.cursor`, returns `nextCursor`, and the scheduler persists it.
- **`since`** (YouTube) — it does not. The provider filters on `schedule.lastSyncedAt` and
  pages internally within the one call, returning `nextCursor: null`.

Both fields are on `PostSchedule` and both are session-scoped: a cursor from three weeks
ago is likely expired, and elapsed time measured across a disabled period is noise in
`commentVelocity`. Guessing the mode wrong silently drops or re-processes comments, which
is why it is a declared constant rather than inferred behaviour.

Re-ingesting is safe regardless — `@@unique([userId, platform, platformCommentId])` makes
every ingest an upsert, so a re-scan costs quota and never correctness.

## Quota is charged inside the provider

The provider knows which operation it is performing, so it is the only place that knows the
cost. Before the call it charges `PLATFORMS[p].budget.costPerRead` or `costPerWrite`
against the declared `scope` (`app` for Meta's pooled hourly window, `project` for
YouTube's daily units) and throws `ThrottledError` locally if the budget is gone, without
spending a call to be told so.

**Known gap, carried from §1.4:** a per-post signal cannot express platform-wide
exhaustion. If YouTube's project quota is gone until midnight Pacific, the next claim still
grabs a batch of YouTube posts and burns one local rejection per row discovering it. The
fix is a platform-level budget row the claim query consults; deferred as disproportionate.

## The two providers

| Provider | Exercises |
|---|---|
| `InstagramProvider` | `cursor` sync, pooled app-scope budget, depth 1, 2200 chars, permanent unavailability (Story) |
| `YouTubeProvider` | `since` sync, fixed project-scope budget, write costing 50x a read, depth 5, 10 000 chars, transient unavailability (private video) |

The pair is chosen to diverge rather than to look plausible: they disagree on sync
mechanism, budget unit, budget scope, read-vs-write cost, thread depth, length limit, and
credential shape. An interface that holds both is unlikely to break on the third.

**Neither calls a real API, which is why there is no third emulating provider.** Both
generate comments on a schedule and accept writes locally; a `PlatformEmulator` alongside
them would be emulating the emulation, and its capability values would be invented rather
than describing anything.

Each therefore takes an **injected failure mode** — throttle, unavailable, 5xx — so
`ThrottledError`, `PostUnavailableError` and a retry are all reachable from Swagger UI
without credentials or a network, against the same two registry entries a reviewer can
read. That is what makes the backoff and retry paths demonstrable rather than merely
described.

## Where a platform splits into two classes

Not yet, and the trigger is concrete: **when read and write no longer share a transport.**
YouTube is the near case — a project-keyed read client and an OAuth write client are
genuinely two HTTP clients with two auth flows, and once the shared surface is only the
response mapper, one class holding both is hiding two things rather than unifying them.

Splitting is local: bind `YouTubeReader` to `ICommentReader` and `YouTubeWriter` to
`ICommentWriter` in `YouTubeModule`. The registry, the workers and every call site are
unchanged, which is the reason the interfaces were separated before there was a class that
needed it.

The same reasoning names the other extraction that has not happened: `QuotaPolicy` when
throttle parsing outgrows a few lines per platform, or when a platform needs quota *state*
a provider should not own — a running daily tally, a reserve held back for writes, a money
budget.

## Known gap: platform writes are not idempotent

No platform offers an idempotency key on comment creation. A `createReply` that times out
after the platform accepted it will double-post when the publisher retries.

The schema narrows the window rather than closing it: `isAuthor` is derived from the
platform's own response, so the next poll ingests the orphaned reply as ours, and the
unique on `(userId, platform, platformCommentId)` makes that an upsert instead of a
duplicate row. What remains is a genuine double-post visible to the audience, bounded by
how long the retry takes relative to the next poll.

Closing it properly needs a pre-write reconciliation read — list recent comments on the
parent, look for one of ours matching the text — which costs a read per retry against a
budget where a YouTube write already costs 50. Deliberately not built; recorded so it is
not mistaken for an oversight.
