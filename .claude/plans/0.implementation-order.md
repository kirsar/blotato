# 0. Implementation order

The sequence for actually writing the code. Design is settled in files 1-5; nothing here
re-decides anything. Two rules shape the order: **every phase ends with something
observable**, and **contracts land before the things that implement them**.

Rough total ~18-19 hours. The cut list is at the bottom.

**Two things that fail silently, both wired early on purpose:** the Swagger CLI plugin only
runs under the Nest CLI (phase 0, asserted in phase 4), and class-transformer drops the
discriminator property unless told not to (phase 6). Each renders a working-looking build
whose demo is hollow.

## 0. Toolchain — 30 min

Replace `package.json` wholesale: `@nestjs/common`, `@nestjs/core`,
`@nestjs/platform-express`, `@nestjs/swagger`, `class-validator`, `class-transformer`,
`reflect-metadata`, `rxjs`, a cuid library, and dev deps `@nestjs/cli`, `prisma`,
`typescript`, `vitest`, `supertest`. Drop `express` and `zod` — the current manifest is for
a different project.

`tsconfig.json` needs `experimentalDecorators`, `emitDecoratorMetadata`, `strict`, and the
path aliases (`@domain/*`, `@platforms/*`, `@repository/*`). `nest-cli.json` needs the
`@nestjs/swagger` plugin enabled — without it no schema is inferred from the DTOs.

**The dev runner must be `nest start --watch`, not `ts-node-dev`.** The Swagger plugin is a
TypeScript transformer declared under `compilerOptions.plugins` in `nest-cli.json`, and the
Nest CLI is what reads that file and injects it into compilation. `ts-node-dev` never looks
at `nest-cli.json`, so the transformer never runs, no metadata is emitted, and **Swagger
renders every DTO as an empty object with no error anywhere** — routes present, schemas
blank. That failure lands on the one thing the whole scope leans on, so the runner is not a
free choice.

Two consequences to hold on to. The plugin infers types, optionality and some validator
decorators, but **not enums, arrays of unions, or examples** — those still need explicit
`@ApiProperty`. And `vitest` compiles through its own pipeline, so the plugin does not run
there either; that matters only if a test asserts on the OpenAPI document.

## 1. Schema — 30 min

**Early, not late.** Writing it forces the domain types to be right, and a mistake here is
cheapest before anything depends on it.

`prisma/schema.prisma` transcribed from [5.storage.md](./5.storage.md). Then
`prisma validate`, and `prisma migrate diff --from-empty --to-schema-datamodel
prisma/schema.prisma --script > prisma/init.sql`, committed. Append the raw partial unique
index for idempotency, which Prisma cannot express. Add both as npm scripts so they run in
CI rather than from memory.

✅ **Observable:** generated Postgres DDL a reviewer can read — enums, composite uniques,
extension tables.

## 2. Domain — 1 h

`/domain`: the enums, the six entity types, `errors.ts` (the `AppError` hierarchy plus the
six-error platform taxonomy), and `automation.ts` — `rank()` and
`effective(user, composition, schedule)`.

`automation.spec.ts` first, because the three-rung `min` with `?? REPLY` as the identity is
the one piece of logic where a wrong answer silently disables replies.

✅ **Observable:** a green test over the kill-switch semantics.

## 3. Storage — 1.5 h

`repositories.contract.ts`, `tokens.ts`, `ids.ts`, then `InMemoryRepository<T>` — primary
`Map`, declared unique keys in secondary maps, clone on read and write. The five concrete
repositories add only their own query methods. `seed.ts` creates the user and the connected
accounts.

Test the two load-bearing uniques: `(userId, idempotencyKey)` rejecting a conflicting
replay, and `(userId, platform, platformCommentId)` making a re-ingest an upsert. A fake
that skips these agrees with the design instead of testing it.

✅ **Observable:** constraint tests green.

## 4. Web skeleton — 1 h

`main.web.ts`, `api-root.module.ts`, `ApiKeyGuard`, `AppErrorFilter`, `HealthModule`,
`openapi.ts` with `DocumentBuilder` and `SwaggerModule.setup`.

**Prove the Swagger plugin is actually running, here, with a test rather than by eye.**
Fetch `/docs-json` and assert a known DTO has non-empty `properties`. Three lines, and it
turns the silent failure described in phase 0 into a red test on the day the wiring is
written instead of a discovery in phase 14. Add one throwaway DTO if no real one exists
yet.

✅ **Milestone — everything after this is verifiable in a browser:** the server boots,
`/health` answers, `/docs` renders, and its schemas are populated.

## 5. First vertical slice: accounts and platforms — 45 min

`GET /v1/accounts` returning `Omit<SocialAccount, 'credentialRef' | 'userId'>`, and
`GET /v1/platforms` serving the registry. Two single-repository reads that prove the whole
path — guard → controller → repository → projected response — and demonstrate the
credential exclusion being enforced by the type rather than by a mapper.

✅ **Observable:** seeded accounts visible in Swagger, which is the demo's entry point.

## 6. Compositions — 2 h

`POST /v1/compositions` and `GET /v1/compositions/:id` with posts embedded and extension
rows written. Validate everything, then commit synchronously with no `await` in the block —
that is what makes it all-or-nothing in memory.

**Build the service-side switch first, then the DTO union.** Mapping `options` onto the
right extension row needs an explicit switch on `platform` regardless, so writing that first
means the endpoint works before any discriminator does, and the typed union becomes an
enhancement rather than a dependency. This is the fiddliest corner of the build and it is
load-bearing — the endpoint exists to make the extension mechanism visible — so it should
not have a single point of failure.

**Discriminate the post item, not `options`.** A discriminator property has to sit on the
object being transformed, and `platform` is on the post, not inside `options`. So the shape
is a `CreatePostDto` base with `InstagramPostDto` and `YouTubePostDto` subtypes, each
carrying its own `options` type. The JSON on the wire is exactly as
[2.api-surface.md](./2.api-surface.md) shows it; only the class structure differs from what
that example implies.

Three specifics that each cost an hour if missed:

- `@ValidateNested({ each: true })` with `@Type(() => CreatePostDto, { discriminator: …,
  keepDiscriminatorProperty: true })`. **That flag is not optional** — class-transformer
  strips the discriminator property by default, so `platform` silently disappears from the
  validated object.
- The Swagger plugin does **not** infer a union. This needs `@ApiExtraModels` plus an
  explicit `@ApiProperty({ oneOf: refs(…), discriminator: { propertyName: 'platform',
  mapping: … } })`.
- `ValidationPipe` wants `transform: true`; `forbidNonWhitelisted` interacts badly with
  discriminated subtypes and should stay off until the union works.

**Fallback if class-transformer fights back** (it has rough edges with nested arrays plus
`whitelist`): make the DTO's `options` a `Record<string, unknown>` and keep the `oneOf`
purely as documentation. The generated client still gets a typed union and Swagger still
shows it — only automatic runtime validation is lost, and the service's own switch already
performs it against the registry.

✅ **Observable:** a composition with an Instagram and a YouTube post, each carrying its
extension, and a typed union visible in `/docs`.

## 7. Comments — read — 1 h

`GET /v1/comments` with `postId` XOR `compositionId`, `parentCommentId`, `since`/`until`,
paging; `GET /v1/comments/:id`. The `400` rules for both ids together and for
`platform`/`accountId` alongside `postId`.

## 8. Platform ports and providers — 2 h

`comment-provider.contract.ts`, `credential-store.contract.ts`, `provider-registry.ts` with
`@PlatformProvider()` discovery, `fake-credential-store.ts`, then `InstagramProvider` and
`YouTubeProvider` — generated comments, optimistic writes, per-provider injected failure
modes, and the extension-row check that makes a Story permanently unavailable without a
call.

✅ **Observable:** every error in the taxonomy reachable on demand.

## 9. Comments — write — 1.5 h

`POST /v1/comments` with the `CommentIdempotencyInterceptor` and capability validation
(`maxCommentLength`, `maxReplyDepth`, `supportsComments`). `DELETE /v1/comments/:id`
answers `501` — it's designed to mark the comment for deletion and let the worker
deliver it, same as a reply, but that worker doesn't exist yet.

✅ **Observable:** the manual reply path complete except delivery — `201 queued`,
`Location`, and a replay returning the same comment.

## 10. Agent — 1 h

`reply-generator.contract.ts`, `stub-reply-generator.ts`, and `batching.ts` — partition by
`(userId, accountId)`, `assertSingleKey`, size caps from the registry.

`batching.spec.ts` covers the partitioning and the cross-tenant assertion. This is the
security-relevant test in the build.

## 11. Scheduling — 45 min

`scheduling.ts`: target-yield interval, geometric backoff on empty polls, jitter, the
retire threshold. Pure functions over plain numbers, so `scheduling.spec.ts` needs no I/O.

## 12. Automation endpoints — 1 h

`PUT`/`DELETE`/`GET` on `/v1/compositions/:id/automation`. Materializes and retires
`PostSchedule` rows and returns `requested`/`ceiling`/`effective`.

**Before the pipeline deliberately** — nothing is due until these rows exist, so the
pipeline would have nothing to claim.

✅ **Observable:** turning automation on creates schedules across every post in a
composition.

## 13. Pipeline — 2 h

`comment-pipeline.service.ts`: claim → read → generate → write, with step 3 querying the
claimed posts rather than consuming step 2's output. Then `worker.module.ts` and
`main.worker.ts` with the `setTimeout` loop.

`pipeline.spec.ts` runs one pass end to end against the fakes.

✅ **Milestone — the system works:** turn automation on, wait a tick, and audience comments
appear with our replies against them.

## 14. `501` routes and polish — 45 min

`not-implemented.controller.ts` for every designed-but-unbuilt route, tagged
`Designed — not implemented`, same error envelope. Commit `openapi.json`.

## 15. README — 1 h

How to run, the demo walkthrough, and the omissions table lifted from
[1.overall-architecture.md](./1.overall-architecture.md). This is the highest-value hour in
the build and the easiest to skip; do not skip it.

## Ordering constraints that actually bind

- **Schema before domain.** The types are transcribed from it.
- **Contracts before providers**, and **providers before the write path** — `DELETE` calls
  a writer synchronously.
- **Automation before the pipeline.** No schedule rows, nothing to claim.
- Everything else can move.

## If time runs short

Cut in this order, and say so in the README rather than leaving it silent:

1. The YouTube provider — Instagram alone still exercises the registry and the ports; the
   pair is what makes the abstraction convincing, so cut this reluctantly.
2. `api.e2e-spec.ts` — the unit tests over `automation`, `batching` and `scheduling` carry
   more weight per minute, because they cover the logic that is actually subtle.

(`DELETE /v1/comments/:id` is already `501` by design, not a fallback cut — see phase 9.)

**Never cut:** the schema and `init.sql`, the batching assertion test, and the README.
Those three are what a reviewer reads first.
