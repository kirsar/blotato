# 4. Agentic Integration (to produce comments) — implementation plan

Decisions and rationale: [0.foundational-research.md](./0.foundational-research.md) §4. Worker wiring is
[1.overall-architecture.md](./1.overall-architecture.md); the claim-and-process loop is
[0.services.md](./0.services.md) under Content Generator. **This file owns the generator
port and the batching rules** — which comments may share one call, and how large that call
is allowed to get.

## The generator is a stub, on purpose

```ts
type PostComments = [Post, Comment[]];

interface IReplyGenerator {
  generate(batch: PostComments[]): Promise<Comment[]>;
}
```

The built implementation returns `` `Reply to ${comment.text}` `` truncated to the
platform's `maxCommentLength`. No token accounting, no cost budget, no conversation
context, no model selection. Swapping it for a real provider is a token rebinding, exactly
like the repositories.

**No new types, unlike the platform port.** The pipeline has just loaded these rows in step
2, and the tuple groups each post with its pending comments structurally — so the post's
content appears once per group rather than being deduped by id, and `maxCommentLength`
comes from `post.platform` through the registry rather than being passed alongside.

**The return is outbound `Comment` rows, and this is the real difference from
[3.social-media-integration.md](./3.social-media-integration.md).** A platform provider
cannot return a `Comment` because it returns comments written by *strangers*, whose
`isAuthor` and parent resolution need lookups it has no access to. The generator returns
*our own replies*, and every field of one is derivable from the parent it was handed:
`userId`, `postId`, `accountId`, `platform` and `platformParentCommentId` all come off the
parent row, and `isAuthor` is `true` by construction. The only foreign thing in the whole
result is the text.

That is also why the flat array needs no keying: each reply carries `parentCommentId`, so
it says for itself which comment it answers. A comment the generator skipped is simply
absent.

**Deterministic failures come back as rows too**, at `status: failed` with an `errorCode`,
rather than through a separate outcome union. The caller persists whatever it is handed —
one write path for successes, skips and refusals alike (see *Failures*, below).

That is not a shortcut around the hard part — it *is* the shape of the hard part. Nothing
about which comments may safely share a call, or how many may, depends on what the model
says. Emulating the text keeps the demo deterministic and testable while leaving the
genuinely load-bearing logic — partitioning and sizing — real code.

**§4.5's demand levers are why batching exists at all.** The Content Generator is bound by
an external provider's ceiling rather than our own infrastructure, and adding workers
cannot raise a ceiling. Cutting the number of calls is the lever that works.

## What gets selected, before any batching

Eligibility is a filter, not a batching concern. The pipeline's single claim is over
`PostSchedule` ([1.overall-architecture.md](./1.overall-architecture.md)), so this runs
against the comments hanging off the posts that pass already claimed. A comment is a
generation candidate when all of these hold:

| Condition | Why |
|---|---|
| `isAuthor = false` | never generate a reply to our own reply |
| no existing reply | backed by `@@index([parentCommentId, isAuthor])` — the "already replied?" probe, answered from the index without reading rows |
| `status = posted` | it is live on the platform and not since deleted |
| depth allows a reply | with `maxReplyDepth: 1`, the target must itself be top-level |
| `effective(post) >= DRAFT` | the three-rung `min` from [5.storage.md](./5.storage.md). `collect` ingests and stops here |
| post schedule not retired | a retired post is no longer being watched |

**Plus one cheap pre-filter: low-signal comments never reach the generator.** An
emoji-only or sub-threshold comment is discarded before the call, which is §4.5's first
demand lever and the only one that reduces volume rather than repackaging it. It costs a
predicate and saves a proportion of every batch.

**`effective(post) >= DRAFT` is the honest form of the gate**, though `draft` never ships
([2.api-surface.md](./2.api-surface.md)), so in practice the generator runs only for posts
at `reply`. Writing the comparison against the rung rather than against the literal keeps
the enum's ordering load-bearing in one more place.

## Batch partitioning — the rules that cannot be relaxed

**The batch key is `(userId, accountId)`.** Every comment in one generation call shares
both. This is the section's whole point, and each dimension is there for a distinct
failure it prevents.

| Dimension | Partitions because | What breaks without it |
|---|---|---|
| `userId` | tenant isolation | one tenant's comment text — audience PII under §6 — appears in the prompt that produces another tenant's reply. A leak and a wrong answer at once |
| `accountId` | one voice per connected account | an agency runs several brands under one tenant. A reply written in brand X's register, posted as brand Y, is wrong even though nothing crossed a tenant line. Credentials and per-account budget follow the same boundary |
| *(platform)* | already implied | `accountId` determines it. Listed because the *reason* is independent: `maxCommentLength` is a prompt constraint, and one call cannot reliably hold "some of these under 150 characters, others under 2200" |

**The worker bypasses RLS, and that is why partitioning has to be enforced rather than
observed.** Row-level security protects the API path, where a session sets
`app.user_id` and Postgres filters every read. The Content Generator claims across *all*
tenants by design — it runs as a privileged role, so no database-level guard is active on
this path at all. The batch key is the only thing standing between a claim batch and a
cross-tenant prompt.

So it is an assertion, not a convention:

```ts
function assertSingleKey(batch: PostComments[]): void {
  const [[first]] = batch;
  for (const [post, comments] of batch) {
    if (post.userId !== first.userId || post.accountId !== first.accountId) {
      throw new BatchIntegrityError(post.id);
    }
    for (const c of comments) {
      if (c.userId !== first.userId || c.accountId !== first.accountId) {
        throw new BatchIntegrityError(c.id);
      }
    }
  }
}
```

It runs immediately before the generator call, costs one pass over a few dozen rows, and
fails the whole batch rather than degrading. A partitioning bug that ships silently is
indistinguishable from correct behaviour until a customer sees another customer's words.
Checking the comments as well as the posts is not redundant: `Comment.userId` and
`accountId` are denormalized, and this is the one place a mismatch between them and the
post's would matter.

**One property this shape gives up, stated rather than hidden.** Passing whole entities
means the tenant identifier is inside the payload, so the "a prompt cannot leak what it
never received" guarantee no longer comes from the type. Containment moves into the
prompt-assembly function, which reads only `content` and `text` off the rows it is given.
That is a weaker guarantee — enforced by one function rather than by the signature — and
it is the price of not maintaining a parallel type. Acceptable here because the assertion
above runs first and the assembly function is a dozen lines; worth revisiting if the
generator ever becomes a service someone else operates.

### What deliberately does *not* partition

**`postId` does not.** Batching per post would be the conservative choice and it collapses
batch size to whatever a single post has pending — frequently one or two — which defeats
the entire purpose. Several posts share a call, each as its own `[Post, Comment[]]` tuple,
so a post's content appears once no matter how many of its comments are in the batch.

That has a real cost worth stating: the model can mis-associate a comment with the wrong
post's context. It is a prompt-structure problem, not a correctness boundary, and it is
mitigated structurally — the grouping is in the input shape rather than in id references,
and every returned reply carries the `parentCommentId` it was built from, so a mismatch
cannot silently redirect a reply to the wrong comment. The failure mode is a lower-quality
reply, never a reply on the wrong post or the wrong account.

**Language, sentiment and thread depth do not partition either.** None of them has a
correctness basis, and each would fragment batches for a quality intuition that a stub
generator cannot even exhibit.

## Maximizing the batch, and what caps it

Four ceilings apply, and the effective size is the minimum:

- **Output budget.** Every comment may produce up to `maxCommentLength` characters, so
  `floor(outputBudget / maxCommentLength)` bounds the batch. This is why the cap is
  per-platform and not a constant: Instagram at 2200 characters batches several times more
  than YouTube at 10 000. The registry constant that already constrains generation also
  sizes the call.
- **Input context.** Comment text is per comment and irreducible; post content is shared,
  and paying for it once per post is a genuine saving because pending comments cluster
  heavily on a few active posts. That is what the tuple shape buys — the grouping is the
  dedupe.
- **Claim duration.** A larger batch holds its rows locked longer, so a worker crash
  strands more of them until the lock ages out. Batch size trades directly against recovery
  latency.
- **Retry blast radius.** A provider-wide failure re-does the whole call, so an oversized
  batch multiplies the cost of every transient error.

**The demo uses a configured maximum and ignores the token arithmetic**, per scope — the
stub has no token cost to divide. The formula is recorded because it is where the real cap
comes from, and because it is derived from a registry constant that already exists rather
than from a new tuning knob.

## Reconciling with the capacity model: the mean says no, the tail says yes

[0.services.md](./0.services.md) computes that a 300-second window holds ~0.15 eligible
replies per account, so a per-account batch averages **~1.07 items** — and concludes that
prompt caching, not batching, is what makes the cost work. That arithmetic is right, and it
settles the *average* case: batching buys nothing in steady state.

It does not settle the case that matters. **Arrival is not uniform, and the whole reason
this service is the system's bottleneck is the tail.** One post going viral puts hundreds
of comments on a single `(userId, accountId)` within minutes — the same minutes in which
the provider's rate ceiling actually binds. Sizing the mechanism against the mean would
mean having no mechanism precisely when the ceiling is reached.

Batching is therefore a **burst absorber, not a throughput optimization**, and it is nearly
free to keep: a batch that does not fill is a batch of one, which is exactly the
unbatched call the capacity model assumes. The cost is the partitioning code — which is
the part worth having regardless, since a batch only grows under load, and load is when a
partitioning mistake would be widest.

One correction to that section's phrasing: batching across a *tenant's own* accounts would
not mix tenants. It is ruled out here for a different reason — brand voice is per account,
so an agency's two brands cannot share a preamble — and the token overhead argument stands
either way.

## Failures are per item; the batch is transport, not a transaction

Every returned row is validated independently — non-empty `text`, within
`maxCommentLength`, and a `parentCommentId` that was actually in the batch. One bad reply
fails alone; the rest are written and published in the same pass.

The two failure classes are genuinely different, and treating them the same is what would
require machinery this design does not have:

- **Provider-wide** — throttle, 5xx, timeout. Nothing is written, the worker backs off at
  the *loop* level, and the same comments come back on the next pass that claims the post.
  Idempotent because no state changed, and correct because an outage is never per-comment.
- **Per-comment and deterministic** — refused content, an over-length reply, a malformed
  row. It is persisted at `failed` with its `errorCode`, which both records the result for
  the caller and removes the comment from the eligible set, since the "already replied?"
  probe now finds a row.

**That split is why generation needs no retry state of its own.** Per-row bookkeeping would
mean churning columns on the largest table in the schema. Neither class wants it: the
failure that recurs is provider-wide and belongs to the worker's own backoff, while the
failure that is per-comment is deterministic and should not be retried at all.

An over-length reply fails rather than being truncated: silently cutting a reply changes
what it says, and `maxCommentLength` was already fed to the generator as a constraint, so
exceeding it is a generator defect worth surfacing.

**Non-determinism forces the write to be immediate** (§4.4). A generated reply cannot be
reproduced, so it is persisted the moment it is returned — never buffered across the rest
of the batch — and the row is written directly at `queued` since no promotion step exists.

## Guardrails: what ships, and what §4.2 still designs

What ships is a pipeline with the guardrails at both ends: `maxCommentLength` as a
constraint *before* generation and as validation *after*, the low-signal filter before,
the three-rung automation cap gating whether generation happens at all, and the batch-key
assertion protecting the call itself.

**§4.2's `guardrailCheck` record — moderation result, model id, confidence, attached
before promotion — is not built, and the reason is structural rather than budgetary.** It
exists to be checked at the `draft → queued` promotion step, and no promotion step ships,
so there is nothing for the record to gate. It becomes necessary the moment either `draft`
or BYO-agent (§1.3) is real, and at that point it wants a `GuardrailCheck` model that the
schema does not currently have.

The same reasoning explains the absence of an `actorType` column (§4.1): the generator is
our own worker, writing through Postgres and never presenting an API key, so a reply's
provenance follows from the code path that wrote it. `createdByApiKeyId` is the form worth
adding, and only once someone else's agent can write.
