  matching platform vocabulary and Blotato's existing `?postId=`. `?compositionId=`

  membership model. Applied across schema, §7.0, §7.2, capacity, security file.
- **`actorType` removed** entirely — the Content Generator is our own worker and never
  presents a key, so provenance comes from the code path. BYO-agent (§1.3) kept as the
  one case that would justify typing keys.
- **Providers: Instagram + YouTube + Emulator** (was Instagram + LinkedIn). Chosen to
  stress the interface — see §5 below.
- **Idempotency**: no separate table. Two nullable columns on `Comment`
  (`idempotencyKey`, `requestHash`) plus a **partial** unique index — ~1 GB rather than
  the ~64 GB a full one would cost, and inbound ingestion never touches it. Contract in
  2.api-surface.md, storage in 5.storage.md, nowhere else.
- **`DRAFT` out of scope** — review step was scoped out in §1.2, so the generator writes
  straight to `QUEUED`.
- **Webhook Delivery** added as a 5th logical service, marked out of scope, with full

### 2b. Code layout and interfaces — decided late in the session, nothing written

| # | Decision | Note |
|---|---|---|
| 10 | **Claim per platform, not one mixed batch.** `WHERE platform = ? AND nextPollAfter < now …`, one claim per platform the instance serves. | Strongest reason is isolation: with a mixed batch, YouTube 429ing hard leaves Instagram rows stalled behind it. Also lets Facebook's batch-fetch endpoint actually pay, and keeps rate-limiter pools per-platform. |
| 11 | **Batch size = `min(dispatcher headroom, remaining platform budget)`.** | This is a better answer to the "account-aware claiming" problem flagged in the review: **platform gates the claim, account gates the dispatch.** Two levels, and the claim itself becomes budget-aware. |
| 12 | **`ICommentProvider` gains `interpretThrottle(err): Backoff`**, returning `{ retryAfter }` \| `{ exhaustedUntil }` \| `{ fatal }`. | Corrects an overstatement: throttle semantics *are* genuinely platform-specific behaviour, not just constants. Meta gives a rolling-hour percentage (exponential backoff is right); YouTube gives a **daily** quota resetting midnight PT, where the correct response is *sleep until reset*, not back off. The provider translates; the scheduler stays uniform. |
| 13 | **Vertical platform modules** — `InstagramModule` owning provider + extension repo + capability seed. **Schedule logic is NOT among them** — same algorithm everywhere, per-platform constants on `Platform`. | Putting schedule logic in a platform module would duplicate the algorithm nine times to vary four numbers. |
| 14 | **`DiscoveryService` (from `@nestjs/core`) + a `@PlatformProvider()` decorator** for iteration — the registry populates itself from metadata, nothing enumerates platforms by name. **Static imports kept** for registration. | Registration and iteration are separate problems. Discovery solves iteration cleanly; a glob-based `PlatformsModule.forRoot()` would remove the import list too (~15 lines, works on Heroku's plain tsc build) but loses static verification. Judged not worth it: adding a platform already needs a provider, a seed row, and maybe a migration — one *appended* line is noise and doesn't conflict. |
| 15 | **OpenAPI is code-first.** DTOs → spec via the `@nestjs/swagger` CLI plugin. Generate the **client** types from the resulting spec (`openapi-typescript`); never generate the server. | Spec-first generators produce awkward Nest controllers, usually drop class-validator decorators, and make round-tripping painful. |
| 16 | **Do not generate the Prisma schema from the API source.** Three layers: Prisma-generated storage types, hand-written DTOs, hand-written mapper between. | The shapes genuinely differ — `CompositionReq { targets: [] }` is nested, storage is normalized. Generating either from the other leaks storage shape into the contract or lets the contract constrain normalization. The mapper is real logic, not boilerplate. |
| 17 | **Two API levels, asymmetric.** Rule: **the level follows the unit of the user's intent.** Watch intent is composition-level (they authored a composition); writes are post-level (a reply goes to one platform); reads accept either. | Matches the current surface — composition-level watch real, post-level documented-only. |
| 18 | **Extension existence is answered by the registry, not by data or catalog introspection.** Per-row: nullable relation via shared PK. **Do not declare extension relations on the base `Post` model** — let the provider's own repository fetch by `postId`. | Declaring them on the base means adding a platform edits the base model, which undercuts the "platform N+1 doesn't touch core" claim. This way `Post` never learns extensions exist. |

## 3. Still open

1. **The `Post` / `Composition` naming trilemma.** You can have API compatibility,
   intuitive naming, or model-API symmetry — any two:
   - **A (current)**: `Post` = platform publication. Compatible + symmetric, but "Post"
     isn't the thing the user wrote.
   - **B**: `Post` = authored, `Publication` = platform level. Intuitive, but `postId`
     then maps to `Publication` → asymmetry, or rename the param and break integrators.
   - **C (ruled out)**: two levels, extensions *are* publications. **Blocked** — see §5.
2. **Five gaps from the end-to-end walkthrough**, none fixed:
   no subscribe endpoint at the time (now partly addressed by the `/watch` pair);
   **inbound comments have no valid `CommentStatus` value** (the enum is all outbound
   reply states); no `GuardrailCheck` model despite §4.2 requiring one; no home for
   per-account budget state; and the `parentCommentId, isAuthor` index (added) needs the
   generator's claim query written against it.
3. **Deletion detection** — forward-only cursor sync structurally cannot see a comment
   disappear, but §6.1 requires it and Blotato's `deleted` status implies they manage it.
   Marked **Open** in current-api-overview.md #11.
4. **Client read volume is still unestimated** — the API service is sized on writes while
   reads are argued to dominate.
5. **Two load-bearing speculations**: the ~30% daily-active fraction and the ~50% share
   of the Meta pool available to comments. Together they swing utilization between ~20%
   and ~64%. Only `X-App-Usage` telemetry settles them.
6. **Whether to extract more** — 0.services.md and 0.capacity-planning.md are out;
   1.overall-architecture.md still holds some prose that could migrate.
7. **Postponed: whether quota handling becomes its own `QuotaPolicy` class.** Current
   answer is no — cost and budget scope are *data* on `Platform`, and only throttle
   interpretation is code, which belongs on the provider that holds the response
   (decision #12). Extract `QuotaPolicy` only if that logic grows past a few lines,
   which for two platforms it won't. The justification if it ever does is change
   cadence: the content API and the quota rules move independently.

## 4. Reasoning worth not re-deriving

**Why the effective Meta ceiling is ~667/sec, not the nominal ~5,556.** Four haircuts:
nominal `200/hr × accounts` → × ~30% daily-active (Meta counts **daily active users**,
not connected accounts) → × 80% safety margin → × ~50% share available to comments
(the pool is shared with the existing publishing product). The corollary is
uncomfortable and worth keeping: **the better this product is at "schedule once and walk
away," the lower DAU goes and the smaller the quota pool gets, while workload is
unchanged.**

**Why polling backoff is load-bearing rather than an optimization.** ~84 of ~110 polls
per post are in the dormant tail. Flat polling was ~22x over the effective ceiling —
*disallowed*, not merely expensive. Decoupling the polling window (~14 days) from the
retention window (45 days) moves utilization from ~64% to ~28%.

**Why batching died and prompt caching replaced it.** At corrected volumes, eligible
replies arrive at ~4.9×10⁻⁴/sec/account, so a 300s window gives ~1.07 replies per batch.
Batching across accounts would mix tenants. Unbatched, each reply pays the full ~400-token
preamble (~615 tokens vs ~240), so cost rises to ~$39k-156k/month — **prompt caching on
the per-user preamble recovers it to ~$16k-65k**. Caching now does the job batching did.

**Why two levels is blocked (option C above).** A foreign key needs one table to point
at, and Postgres offers no way to make nine platform tables one referenceable target, so
`Comment.postId` has nowhere to go. Legacy table inheritance gets the cross-table scan
but **a foreign key referencing the parent does not see rows in children**. Declarative
partitioning requires identical columns across partitions, so no per-platform fields.

**Why `Post` absorbs more variance than expected.** The comment system reads five fields
off a Post: `platformPostId`, `platform`, `accountId`, `content`, `status`/`publishedAt`.
Almost all platform variance in a post is *authoring* variance, and authoring is out of
scope. Same conclusion from the other direction for `PostSchedule`: pagination is an
opaque string everywhere, cursor-vs-timestamp is two nullable columns plus a
`Platform.syncMode` flag, and adaptive-polling state is identical algorithm state with
per-platform *constants*.

**Why Instagram + YouTube stresses the interface.** Budget unit (calls vs weighted units,
insert = 50× list), budget scope (pooled-per-user vs fixed-per-project), read vs write
limits (separate vs shared pool), thread depth (flat vs nested), length (2,200 vs 10,000),
auth artifact (per-account token vs project key + OAuth). LinkedIn was dropped partly
because its rate limits are unpublished, so its capability row would be guesswork.

**Why per-platform content variance needs no `tone` field.** The platform-specific
caption already embodies the tone, and reply generation reads `Post.content`. Adding an
explicit per-platform tone would fragment the cached preamble into N entries per user.

**The headline finding from the review, still true.** The plan was 833 lines with zero
code when reviewed. The numeric half is now thorough and defensible; **the schema and
API correctness half is largely untouched**, and every hour on capacity was an hour not
spent on the deliverable's TypeScript.
