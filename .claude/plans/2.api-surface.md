# 2. API Surface — implementation plan

Decisions and rationale: see [0.foundational-research.md](./0.foundational-research.md) §2. This file
is buildable detail only.

## Proposed REST surface

Keep Blotato's real flat `/v1/comments?postId=` resource with filters (proven design,
avoids two shapes for one job) rather than nesting under `/v1/posts/:id/comments` —
doubly so now that there are *two* possible parents (`Composition` and `Post`): nesting
would mean two URL shapes for the identical list operation, and `postId`/`compositionId`
are mutually-exclusive filters, not a resource location. Detail fetch is already flat
(`GET /v1/comments/:id`), so list stays flat too for the same shape everywhere.

**Two id parameters, because `Composition` 1:N `Post` (0.foundational-research.md §1.2.a):**

- **`postId`** — one published post on one platform. **Same meaning as Blotato's
  existing `/v2/comments?postId=`**, so integrator code carries over unchanged.
- **`compositionId`** — the authored thing. Returns comments across *every* platform it
  was published to, each item carrying its own `platform` and `postId`. This is the new
  capability, and it answers "comments on the thing I wrote."

Exactly one is required; supplying both is a `400`. **`POST /v1/comments` takes
`postId` only** — a reply is delivered to one platform, so a composition id would be
ambiguous. That asymmetry is deliberate: reads may aggregate, writes always target.

Note the new capability arrives as a *new* parameter rather than a redefinition of
`postId`. Redefining an existing parameter to aggregate would silently change results
for callers who never asked for it.

**`platform` and `accountId` are only meaningful alongside `compositionId`.** A `Post`
already determines both — it belongs to exactly one account on exactly one platform — so
combined with `postId` those filters can only be a no-op or a contradiction. Neither is
something a client meant to write, so both are a **`400`** there rather than silently
ignored. With `compositionId` they narrow a genuinely multi-platform result set, which
is the case they exist for.

## The full surface

**Everything below is in the OpenAPI document.** Unbuilt endpoints are real routes that
return **`501 Not Implemented`** with the standard error envelope, tagged
`Designed — not implemented`. That's deliberate: OpenAPI is cheap, a 404 would be
indistinguishable from a typo, and a well-formed 501 proves routing and the error
envelope work while stating plainly that the handler doesn't exist. A reviewer can
exercise every route in Swagger UI and always get a truthful answer.

| Method | Path | Purpose | Status |
|---|---|---|---|
| **Comments — the task's literal requirement** ||||
| `GET` | `/v1/comments` | List. Query: **one of `postId` or `compositionId` (required)**, `parentCommentId?`, `since?`, `until?`, `cursor?`, `limit?` (default 25, max 100). **`platform?` / `accountId?` only with `compositionId`** — see below. Returns `{ items, cursor }`. | **Real** |
| `GET` | `/v1/comments/:id` | Single comment — poll `status` after a reply. | **Real** |
| `POST` | `/v1/comments` | Reply, or post a top-level comment. Body `{ postId, text, parentCommentId? }`, optional `Idempotency-Key`. **201** at `status: "queued"`, `Location` header. | **Real** |
| `DELETE` | `/v1/comments/:id` | Delete our own reply. `204`. | **Real** |
| **Automation — our tier-2 feature (§0)** ||||
| `PUT` | `/v1/compositions/:id/automation` | Turn automation on for every `Post` under this composition — fan-out. Empty body runs at the account's authorized level; optional `{ level }` may **lower** it. Idempotent `204`; `422` on an attempt to raise. | **Real** |
| `DELETE` | `/v1/compositions/:id/automation` | Turn it off — fan-out. `204`. | **Real** |
| `GET` | `/v1/compositions/:id/automation` | `requested` / `ceiling` / `effective` level, plus per post `lastSyncedAt`, `nextPollAfter`, `retiredAt`. | **Real** |
| `PUT` / `DELETE` | `/v1/posts/:id/automation` | Same at single-platform granularity. | `501` |
| **Resolution reads — so `postId`/`compositionId` point at something** ||||
| `GET` | `/v1/compositions/:id` | id, `content`, `createdAt`, **and its `posts[]` embedded** — the only way to resolve a `postId`, see below. | **Real** |
| `GET` | `/v1/posts/:id` | Single post. Redundant — compositions already embed theirs. | `501` |
| `GET` | `/v1/accounts` | Connected accounts: `id`, `platform`, `platformAccountId`, `displayName`. Read-only — connecting an account belongs to the existing product. | **Real** |
| `GET` | `/v1/platforms` | **Capability discovery** — per platform: `supportsComments`, `supportsDelete`, `maxReplyDepth`, `maxCommentLength`, `enabled`. Serves the code registry (5.storage.md), not a table. | **Real** |
| `GET` | `/v1/compositions` · `/v1/posts` | Paginated lists. | `501` |
| **Authoring — normally another system's surface** ||||
| `POST` | `/v1/compositions` | Create a composition and its `posts[]`, each carrying platform-specific `options`. **Real** — the extension-mechanism showcase and the demo's only data-entry path; see below. | **Real** |
| `PATCH` | `/v1/posts/:id` | Edit one platform's caption. | `501` |
| `DELETE` | `/v1/compositions/:id` · `/v1/posts/:id` | Unpublish/remove. | `501` |
| **Subscriptions — we notify the customer (0.current-api-overview.md #5)** ||||
| `POST` | `/v1/subscriptions` | Register a signed endpoint. **One resource, scope in the body** — see below. | `501` |
| `GET` · `DELETE` | `/v1/subscriptions[/:id]` | List and revoke. | `501` |
| **Operational** ||||
| `GET` | `/health` | Liveness (§10.1). Outside `/v1` — not part of the versioned contract. | **Real** |

**Twelve real endpoints**: four comment operations, three automation operations, two
composition operations, account listing, capability discovery, and health. Everything else
answers `501`.

`GET /v1/platforms` earns its place as the cheapest possible demonstration of the
brief's "support more platforms" requirement — one repository read, and the capability
model becomes visible without a reviewer having to construct a failing request.
`GET /v1/accounts` is the same shape one layer down and exists for a concrete reason:
`POST /v1/compositions` requires an `accountId`, so without it the demo has no starting
point. **Read-only, and no credential material is ever in the response** —
`SocialAccount.credentialRef` is a secrets-store id and never leaves the server.
`GET /v1/posts/:id` is the one `501` that's a deliberate omission rather than deferred
work: compositions already embed their posts.

### Comments — notes

**`Comment.status = draft` is out of scope end to end — not just unused, not mentioned
as a possible response.** The pipeline's generation step writes straight to `queued`
(1.overall-architecture.md), and `POST /v1/comments` does the same. The value stays in
the `Comment.status` enum for schema completeness, but no response returns it and no
request body names it.

**No promotion endpoint exists** (no `PATCH /v1/comments/:id` to move a reply between
statuses). Deliberate, not an oversight: promotion has nothing to attach to once nothing
is ever written at `draft`. **This costs only the `draft` automation level** — it alone
needs something to promote. `collect` and `reply` both ship (Automation, below).

**`DELETE` marks the comment for deletion and returns**, the same shape as `POST`: a
capability check (`isAuthor=true` + the registry's `supportsDelete`), then a status
transition the worker picks up and delivers to the platform. `501` for now — the
worker/pipeline that consumes it isn't built yet.

### Automation — one switch, depth from the account's policy

**Named for what it does.** The product's value is that comments get answered, so the
plainest call should do that, not merely start collecting.

**One ordered enum, used for all three roles.** Each level switches on one more worker,
so the vocabulary describes how far down the pipeline a comment travels:

| `level` | Scheduler-Retriever | Content Generator | Reply Publisher | Meaning |
|---|:---:|:---:|:---:|---|
| `off` | — | — | — | nothing fetched, nothing stored |
| `collect` | ✅ | — | — | comments ingested and readable; caller replies by hand |
| `draft` | ✅ | ✅ | — | replies generated, held for review — **out of scope** (needs `DRAFT`, §1.2) |
| `reply` | ✅ | ✅ | ✅ | generated and sent |

The levels are named for what the system does rather than for the human's role, so one
enum serves both a grant and an instruction. **The ordering is load-bearing** — the cap
mechanism is `min(requested, ceiling)`, and `min` needs a ranked set, which is why this
is one ordered enum rather than two.

**Three values, three jobs:**

| | Values | Where it lives | Set by |
|---|---|---|---|
| **`ceiling`** | `off` · `collect` · `draft` · `reply` | account — `User.maxCommentAutomationLevel` | us, as a trust/rollout/contract decision |
| **`requested`** | `collect` · `draft` · `reply`, or absent | `Composition.commentAutomationLevel`, optionally overridden by `PostSchedule.commentAutomationLevel` | the caller |
| **`effective`** | `off` · `collect` · `draft` · `reply` | derived, stored nowhere | `min(ceiling, composition, post)` |

Three levels of the same enum, each able to lower the one above. That's what makes
fan-out `DELETE` non-lossy: it clears composition intent, and any per-post override
survives — and a post published later to a new platform inherits the composition's level
rather than defaulting to off.

- **Empty body** — `requested` is absent, so `effective` = `ceiling`. The common case:
  "do whatever I'm authorized to do."
- **`{ "level": "collect" }`** on a `reply`-ceiling account — `effective` becomes
  `collect` for this composition only. The sensitive-post case.
- **`{ "level": "reply" }`** on a `collect`-ceiling account — **`422`**, never a silent
  downgrade. A caller who believes replies are going out when they aren't is the worse
  failure by a wide margin.
- **`ceiling: off`** — automation cannot be turned on at all, whatever is requested.
  Suspended account, or a compliance hold.

Worked example: ceiling `reply`, requested absent → effective `reply`. Then the account
is downgraded to `collect` → the same composition's effective silently becomes
`collect`, with no write to it. That is the kill switch working, and the reason
`effective` is derived rather than stored.

**These are two different kinds of thing, not two settings of one thing.**
`User.maxCommentAutomationLevel` is a *capability grant* — what this account may do. The
automation call is an *instruction* — what to do with this composition. Grants are
evaluated at use
time, never baked into the resource, for the same reason permission systems don't copy
a user's roles onto every document: **the ceiling has to work as a kill switch.** If the
effective level were stored per composition, revoking an account's autonomy would leave
every existing composition replying at its baked-in level until someone swept them.
Deriving it means dropping the ceiling stops everything on the next poll.

The cost of deriving is that the effective value lives nowhere, so
**`GET /v1/compositions/:id/automation` returns all three** — `requested`, `ceiling`,
and `effective`. One call answers "what will happen, and why," which is what stops a
two-layer model from becoming two places to look.

**`collect` earns its place** rather than being a degenerate case. Cross-platform
aggregation is something no single platform gives you, brands that will never allow
auto-reply still want monitoring, and trust-rollout customers want to observe before
delegating.

**Two of the four levels ship.** `collect` and `reply` are both fully reachable — under
`collect`, comments arrive, the caller reads them and replies through
`POST /v1/comments`, every step a real endpoint. It costs one condition in the
generator's claim query, not a promotion surface. **Only `draft` is out of scope**,
because it alone needs the `DRAFT` status and a promotion step.

### Why `PUT`, not `POST`

Singleton sub-resource, not a collection — there is no `Automation` entity, and even a
hypothetical one would be 1:1 with its parent (`PostSchedule` already *is* that state:
row exists = automated). `PUT`/`DELETE` at a fixed, client-known URI, not `POST`/`201`:
nothing with its own new identity is ever created, and the operation must be safe to
retry, which is `PUT`'s actual contract rather than something to special-case per call.

The composition-level pair ships because it matches how a client thinks — "handle
comments on the thing I posted," without enumerating platforms themselves. The
per-`Post` pair is the same shape at finer granularity, `501` here so the seam is
visible.

Fan-out `DELETE` clears the composition's level; per-`PostSchedule` overrides survive,
since the two are separate rungs of the same cap (above).

### `GET /v1/compositions/:id` embeds its posts — the only resolution path

With `GET /v1/posts/:id` and both list endpoints at `501`, **this is the sole way to
resolve a `postId` into anything meaningful.** A client reading a comment gets a
`postId`; without the embed it could aggregate comments but never learn which platform
each came from or what the post said.

Embedding rather than paginating, because the array is bounded by platform count —
typically one to five, capped by however many accounts a user has connected. Each entry
carries `accountId`, `platform`, `platformPostId`, `content`, `publishedAt`,
and the platform extension where one exists, so it also doubles as the visible proof
that `InstagramPost`/`YouTubePost` are real.

`POST /v1/compositions` requires an `accountId`, which is what `GET /v1/accounts` is for:
seeded accounts are discoverable in Swagger UI rather than copied out of a README, so the
demo has an entry point that doesn't depend on documentation.

### `POST /v1/compositions` — real, for two reasons

Authoring is normally the existing product's job, and this API otherwise only consumes
posts that already exist. It's built anyway:

- **It's the demo's only way in.** Persistence is in-memory, so without a create path a
  reviewer opening Swagger UI has no data and no way to make any. Automation, listing
  and replying all need a composition to exist first.
- **It's where the extension mechanism becomes visible.** The per-platform fields are
  authoring inputs, not just ingestion artifacts — you choose whether a YouTube video is
  `unlisted`, whether an Instagram post is a Reel. So the request body is exactly the
  discriminated union those extensions exist for:

```json
POST /v1/compositions
{
  "content": "shared caption",
  "posts": [
    { "platform": "youtube",   "accountId": "acc_1", "options": { "privacyStatus": "unlisted" } },
    { "platform": "instagram", "accountId": "acc_2", "options": { "mediaProductType": "REELS" },
      "content": "IG-specific caption" }
  ]
}
```

**`platform` is redundant as data and kept only as the wire discriminator.** `accountId`
already determines it — the same redundancy that makes `platform` a `400` on
`GET /v1/comments`. It survives here because `oneOf` + `discriminator` is what gives
`options` a typed union in generated clients, and OpenAPI cannot discriminate on a field
of a resource the client would have to fetch first. The alternative is
`options: Record<string, unknown>`, which would gut the extension showcase that
justifies this endpoint. So it stays, and **contradicting the account's platform is a
`422`** rather than silently trusting either side.

`options` writes the matching `InstagramPost` / `YouTubePost` extension row; a platform
with no extension omits it entirely.

The key is `posts` because the elements *become* `Post` rows, and
`GET /v1/compositions/:id` returns them under the same key — one name for one concept on
both sides, with the response simply adding the server-assigned `id`, `platformPostId`
and `publishedAt`. A post has no `status` — this API never publishes, so a non-null
`publishedAt` is the whole of "is it live" (5.storage.md).

**Why one composition-level call rather than `POST /v1/posts` × N:** atomicity. A
composition with two of its four posts created is an orphan the client has to detect and
clean up, and a partial fan-out is exactly the unlinked-ids problem the `Composition`
layer exists to prevent. One call, one transaction, all-or-nothing.

**It records that a post exists; it does not publish to the platform.** That boundary is
what keeps this from actually becoming an authoring product — no provider write call, no
scheduling, no media upload. `PATCH`/`DELETE` on compositions and posts stay `501` for
the same reason: editing a published post is a real authoring concern, and this one
endpoint is justified by demo mechanics rather than by scope creep.

### Subscriptions — how a customer avoids polling us

**Why it exists, in one line:** so our customers can stop polling `GET /v1/comments`.
Otherwise this design makes *our* polling adaptive and then hands the identical problem
to every integrator, who has none of the velocity signal needed to be adaptive about it.

**One resource, scope in the body — not three endpoints.** A subscription is the same
thing at every granularity; only its filter differs, so splitting it into
`/compositions/:id/subscriptions` and friends would be three URL shapes for one
operation, the same argument that keeps comment listing flat.

```json
POST /v1/subscriptions
{
  "url": "https://customer.example/hooks/comments",
  "events": ["comment.created", "comment.reply.posted"],
  "scope": { "compositionId": "cmp_123" }
}
```

`scope` takes **at most one** key, and omitting it means everything the caller owns:

| `scope` | Delivers |
|---|---|
| *omitted* | every comment on every account this user has connected |
| `{ "accountId": "…" }` | everything on one connected account |
| `{ "compositionId": "…" }` | one authored piece, across every platform it went to |
| `{ "postId": "…" }` | one platform's copy of it |

That's deliberately the same aggregate-versus-target axis `GET /v1/comments` already
uses, so a client learns one mental model and reuses it. Supplying more than one key is
a `400`, for the same reason `postId` plus `compositionId` is.

**`events` is broader than comments, and the valuable ones are silent failures.** Sizing
this properly is deferred with the rest of the feature, but the scope is wider than
`comment.created` suggests:

| Family | Example events | What breaks without it |
|---|---|---|
| Comment | `comment.created`, `comment.deleted` | they poll us — the case above |
| **Reply outcome** | `reply.posted`, `reply.failed` | `POST /v1/comments` returns `queued`, so every write needs follow-up polling — and a failed reply nobody hears about is a customer who believes they responded |
| **Watch health** | `post.watch.retired`, `post.watch.unavailable` | polling stops at ~14 days by design, or a post becomes unpollable (private video, disabled comments, a Story) — the customer believes they're monitored and isn't |
| **Account health** | `account.credentials.expired` | comments simply stop; nothing distinguishes "quiet week" from "disconnected weeks ago" |

Two consequences worth flagging before this is built. **Not every event is valid at
every scope** — `account.credentials.expired` scoped to a `postId` is meaningless — so
the resource needs a validity matrix rather than accepting subscriptions that can never
fire. And **reply-outcome events partly obsolete the poll-after-write instruction** on
`POST /v1/comments`, which is worth reconciling rather than documenting both.

**Platform-side callbacks are not part of this API.** Whether we learn about a comment
by polling Instagram or by Instagram notifying us is an internal quota decision
(0.capacity-planning.md §5) with no endpoint a customer ever touches. Nothing is
tunnelled either: a subscriber's event is emitted from *our stored comment row*, so the
platform's payload shape never reaches them and the event is identical however the
comment arrived.

Stays `501` — SSRF protection can't be deferred, so half-building it is worse than not
starting (0.current-api-overview.md #5).

## Error envelope

`{ "error": { "code": string, "message": string, "details"?: object } }` mapped from
the `AppError` hierarchy in `src/domain/errors.ts`. Status codes: `404` (composition/
post/comment not found), `422` (`PLATFORM_UNSUPPORTED`, `MAX_DEPTH_EXCEEDED`,
`TEXT_TOO_LONG`, `AUTONOMY_NOT_PERMITTED`), `429` (`RATE_LIMITED`), `502`
(`PLATFORM_API_ERROR`), `501` (`NOT_IMPLEMENTED`), `409`
(`IDEMPOTENCY_KEY_CONFLICT`).

### Idempotency — the whole contract

`POST /v1/comments` accepts an optional `Idempotency-Key` header. Storage is two nullable
columns on `Comment` and a partial unique index — no separate table (5.storage.md).

| State | Response |
|---|---|
| No row for `(userId, key)` | process, store key + `hash(body)`, `201` |
| Row exists, hash matches | re-serialise that comment and return it |
| Row exists, hash differs | **`409 IDEMPOTENCY_KEY_CONFLICT`** |
| No key supplied | process normally, no deduplication |

**A replay is the same resource, not the same bytes.** Stripe-style idempotency returns
the original response verbatim; this returns the comment as it stands now, so a retry
ten seconds later may show `posted` where the first call said `queued`. That's a
deliberate divergence and the better behaviour here, since the endpoint already tells
callers to poll `status` — a changed status is expected, not a broken contract. It also
means nothing needs storing but the key and the hash.

**The hash is what makes it idempotency rather than a cache.** Without comparing bodies
we'd hand a client the response to a *different* request that happened to reuse a key.
Only successful requests store a key, so a retry after a `4xx` or `5xx` re-processes
normally.

**`501` is documented as a response on every unbuilt route**, same envelope, so a client
sees one error contract everywhere.

## Why this costs almost nothing

Twelve real endpoints, of which three are single-repository reads and one is a health
check.
The `501` routes are a controller method and a throw each. OpenAPI is inferred from the
`class-validator` DTOs by the `@nestjs/swagger` CLI plugin rather than hand-annotated
(1.overall-architecture.md, OpenAPI).

The payoff is disproportionate: persistence is in-memory and providers are mocked, so a
reviewer opens Swagger UI and exercises the whole surface with no database, no
credentials, and no setup — and every route answers truthfully, including the ones that
say they aren't built.
